# Pentest Master

Операторская консоль для задач в разрешённом scope. Данные конкретных задач,
сессии, PoC и сетевые отчёты создаются локально и в исходный репозиторий не входят.

## Архитектура

Требования следующих этапов и граница между реализованным и запланированным:
[docs/PM_REWORK_PLAN.md](docs/PM_REWORK_PLAN.md).

- `pm.py` принимает ввод оператора и управляет жизненным циклом задачи.
- `orchestrator/` планирует работу ролей `recon`, `vuln`, `access`, `verify`,
  хранит факты и проверяет доказательства флагов и целей.
- [instructions/](instructions/README.md) — единый источник общих правил,
  инструкций ролей, профилей специализации и подключаемых процедур. Полный и
  сжатый промпты используют один сборщик. Профиль только сужает инструменты
  и бюджет; scope и разрешения определяются сохранённым заданием и кодом.
- [Версионируемая память задачи](docs/TASK_MEMORY.md) хранит текущее состояние,
  историю изменений и ссылки на полные оригиналы в существующей SQLite/storage.
  Координатор и специалисты видят весь существенный структурированный инвентарь;
  нужные материалы читаются по частям через `pm_task_memory` / `pm_material_read`.
- `executor/` проверяет scope и запускает сетевые инструменты через NetGuard.
- `mcp/server.py` предоставляет инструменты агентам; `integrations/burp-bridge/`
  импортирует метаданные Burp. `runtime/` содержит точки входа и профили.
- `storage/`, сессии и журналы — локальные рабочие данные; они исключены из git.

## Установка

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -m orchestrator.check_environment
.venv/bin/python -m pip check
```

Перед первым сетевым запуском оператор отдельно проверяет/обновляет установленный
root-owned NetGuard broker, VPN и разрешённую область комнаты. Установка Python
зависимостей этого не делает. Новые HTTP/browser/tool/pivot-протоколы требуют
соответствующей версии broker; см. [TOOLS](docs/TOOLS.md),
[HTTP_COMPONENT](docs/HTTP_COMPONENT.md), [SESSIONS](docs/SESSIONS.md) и
[BROWSER_BURP](docs/BROWSER_BURP.md). Рабочая Kali при разработке не настраивается.

Рекомендуемый порядок: проверка окружения → offline/runtime-тесты ниже → отдельная
операторская проверка broker/VPN → `.venv/bin/python pm.py` → «Новая цель» с
явной областью и coordinated → вопросы с ID → обычное «Продолжить». Ключ вводится
штатным скрытым запросом; его не передают в argv и не сохраняют в задаче.
В CLI исходное задание задаётся `new --task` или `--task-file`; для явных целей
используются `--goal-first` и `--objective`, ожидаемое число — `--expect-flags`.
Специалист, завершивший роль, ещё не выполнил цель: новые флаги принимаются
оператором после проверки на платформе.

Завершающая [матрица требований, порядок живой проверки и сбор диагностики](docs/FINAL_ACCEPTANCE.md)
разделяет контракты, настоящие локальные SDK/MCP/HTTP/SSH/Chromium проверки и
непроверенные live-интеграции. Одна Kali, один оператор, без фонового демона.

## Режимы запуска

`new --coordinated` и `resume --coordinated` используют маршрут начальная
разведка → структурированная карта → одно решение координатора → выбранная роль
→ перечитывание состояния. Режим сохраняется в задаче; обычный `resume`
использует его. Для старых задач без метаданных сохраняется прежний маршрут.
Выбор также доступен в интерактивном меню. `attack --coordinated` остаётся
отдельным входом. Флаги и несовместимые комбинации проверяются до сетевых действий.

Цель принимает IPv4, IPv6, домен или HTTP/HTTPS URL. `--area web|host|lab`
задаёт область исследования: сайт, сервисы машины или явно ограниченная среда.
URL/домен по умолчанию идут в web/coordinated без полного скана общего IP.
Исходный URL и query сохраняются; fragment остаётся браузерными данными.
Разрешения origin/Host/SNI отделены от DNS и связей с адресами. CDN-ссылка не
даёт права сканировать CDN. `--page-resource URL` разрешает один supporting URL;
`--allow-network`, `--allow-resource`, `--deny-resource`, `--path-prefix` и
`--ssrf-destination` явно задают границы. Подробности и ограничения:
[RESOURCE_SCOPE.md](docs/RESOURCE_SCOPE.md).

`change-ip TASK_ID --target IP` сохраняет ту же задачу и её материалы/цели/историю,
проверяет известные соединения и продолжает без нового полного скана. Прежний
доступ сохраняется как сведения с неизвестной текущей живостью. Прерванный
running-шаг не запускается заново. Незавершённые старые successor-переходы
по-прежнему можно довести до конца.

ACCESS и использование найденных материалов/кандидатов выполняются автоматически
внутри задания. `--approve-step` и ввод `a:ID` удалены. Классификатор находок
отключён как механизм остановки: Git, секрет, ссылка или изменение доступа сами
по себе не требуют «продолжить». Проверки scope, триажа, бюджета, качества отчёта
и неизвестного исхода сохранены.

Вопросы pivoting, инструментов/документации, бюджета и подтверждения конкретного
флага хранятся в SQLite. `questions TASK_ID` показывает очередь без API и сети;
`--answer ID --decision approve|decline|information --note-file PATH` сохраняет
ответ. В меню это пункт «ВОПРОСЫ». Ветка с вопросом ожидает ответа, независимые
сервисы могут исследоваться дальше. Ответ не расширяет scope/бюджеты; явное
подтверждение выбранного флага использует прежний операторский путь, без создания
сетевого доказательства. Подробнее: [очередь и границы](docs/OPERATOR_QUESTIONS.md).

Запрос инструмента/документации теперь содержит точные источник, версию, действия,
место и права. После явного approve broker сохраняет user/docs в workspace либо
отдельно устанавливает поддержанный APT-пакет. Повторного вопроса при тех же
условиях нет. MCP не может выдать разрешение за оператора; failed/unknown
установки не повторяются автоматически. Фиксированные SYN/UDP/OS-профили Nmap
имеют ограниченные привилегии внутри NetGuard, обычный PoC остаётся без root.
Нужна обновлённая root-owned копия broker с `tool_protocol=1`; при разработке
установленный broker и Kali не менялись. [Протокол, источники и пределы](docs/TOOLS.md).

Общий [менеджер сессий](docs/SESSIONS.md) сохраняет полезные PTY/SSH/callback
между ролями, ограничивает их десятью и выдаёт терминал одному агенту. Живость
перепроверяется; SQLite/PID не считаются доказательством рабочего подключения.
Поддержанный SSH-forward создаётся через очередь pivoting после явного согласия,
без расширения scope и повторного создания при resume. Callback выбирает текущий
VPN-маршрут, а файлы принимаются отдельно потоком с размером/хэшем и результатом
полноты. Для новых операций требуется операторское обновление root broker.

[HTTP-компонент](docs/HTTP_COMPONENT.md) предоставляет свежие запросы с методами,
query, заголовками, сессионными cookies/auth, телами/form/multipart и проверяемыми
редиректами. Оригиналы читаются отдельно через `pm_http_read`; транспортное
завершение не означает успешного входа. Заголовки до 1 MiB проходят настоящий
транспорт. Для этого пути нужен root broker с `http_protocol=1`.

[Сетевое исследование](docs/NETWORK_RESEARCH.md) разделяет discovery, текущую
доступность и service identification. `survey --protocol tcp|udp` использует
сохраняемую очередь; TCP-список — до 50 портов. UDP-молчание остаётся
open|filtered. Preflight продолжает непроверенные пакеты без общего потолка
10 секунд. `target-state` явно сохраняет выключение/восстановление; offline
coordinated использует сохранённые материалы без повторного скана и лишних
модельных решений. Подтверждение флага остаётся доступным без живой цели/capture.

[Обработка материалов](docs/MATERIAL_PROCESSING.md) выбирает обработчик по байтам:
текст/кодировка, ZIP/TAR/gzip, PDF/изображения, статический бинарный анализ и Git
loose/pack/index с delta через штатный Git. `pm_material_import` сохраняет файл
пространства задачи; `pm_material_process` работает и с сохранённым capture.
Оригиналы, производные файлы и ошибки доступны в общей памяти. OCR требует
Tesseract с языковыми данными; при отсутствии создаётся вопрос об установке,
а не вымышленный результат. Внешние LFS/submodule URL не расширяют scope.

[Управляемый JS-браузер](docs/BROWSER_BURP.md) использует Playwright/Chromium,
сохраняет отдельные пользовательские контексты и передаёт их между ролями через
общий менеджер сессий. `pm_browser` выполняет open/fill/click/wait/read; сетевые
запросы проходят существующий scoped HTTP broker и сохраняются вместе с DOM.
Базовый браузер не требует Burp. Дополнительный Pro-адаптер использует настоящий
Montoya API и guarded task-local Proxy, пассивный импорт отделён от отправки.
Здесь проверены реальный локальный Chromium и контракты; живой Burp не установлен
и не считается испытанным. Новые возможности требуют явной операторской
конфигурации/обновления broker, при разработке рабочая Kali не настраивалась.

Качество отчёта (`report_quality`), исход вызова (`execution_outcome`) и
подтверждение цели различаются. Повреждённый ответ сохраняется целиком в
приватном raw-файле; допускается одна ограниченная попытка форматирования в
отдельной Harness-сессии с отключёнными инструментами. При неудаче планирование
останавливается. Явные противоречия сохраняются с исходными утверждениями для
проверки, без публикации подтверждённых фактов/доступа из спорного отчёта.

Просмотр сохранённой паузы не вызывает модель, preflight или восстановление
namespace, в том числе `resume TASK_ID --diagnostic`. Диагностический флаг меняет
только отображение. `--continue-coordinated` после повреждения явно признаёт отчёт
неполным и разрешает перепланирование; завершённая проверка не повторяется
автоматически. Прерванный running-шаг требует отдельного рассмотрения.
В консоли номер зарезервированного отчёта не означает существование файла.
`completed` роли и exit_code=0 не означают достижения исследовательской цели.

## Evidence Hub (отдельный анализ / прежний маршрут)

Evidence Hub связывает завершённые сетевые исследования и метаданные Burp
Proxy History в доказательный пакет для четырёх ролей. Для существующей задачи
задайте её номер в переменной `TASK_ID`:

```bash
TASK_ID=1  # замените на номер своей задачи
# 1. Сверка двух источников без токенов и без сетевой активности
.venv/bin/python orchestrator/evidence_pipeline.py status --task-id "$TASK_ID"

# 2. Четыре анализа модели по объединённым наблюдениям
.venv/bin/python orchestrator/evidence_pipeline.py agents --task-id "$TASK_ID"

# 3. Повторно: никаких API-вызовов, если данные не изменились
.venv/bin/python orchestrator/evidence_pipeline.py resume --task-id "$TASK_ID"
```

Когда Burp открыт и появились новые HTTP-запросы:

```bash
# Импорт и обновление пакета доказательств без LLM
.venv/bin/python orchestrator/evidence_pipeline.py sync --task-id "$TASK_ID"

# Анализ новой версии пакета (ключ API потребуется снова)
.venv/bin/python orchestrator/evidence_pipeline.py agents --task-id "$TASK_ID"
```

Для полного действия одной командой при **запущенном Burp**:

```bash
.venv/bin/python orchestrator/evidence_pipeline.py run --task-id "$TASK_ID"
```

В `run` сначала синхронизируется Burp History, затем при необходимости выполняются 4 вызова модели. В режиме `agents` сеть не сканируется и Burp не требуется.

## Новые таблицы SQLite

- `evidence_snapshots`: слепки набора наблюдений с SHA-256.
- `evidence_agent_reports`: 4 отчёта на **версию** слепка, без удаления старых отчётов.

Хеш не меняется при повторных запусках без новых наблюдений. При появлении нового Burp наблюдения слепок меняется; старые отчёты сохраняются, а новые агенты могут сформировать новые версии отчётов.

## MCP сервер

`integrations/evidence_hub_mcp.py` — отдельный `stdio` MCP сервер с инструментами:

- `evidence_status(task_id)` — получить структурированные подтверждённые сетевые наблюдения и метаданные Burp;
- `evidence_sync_burp(task_id,limit)` — подтянуть метаданные из локального Burp без запросов к тестируемым целям.

Сервер **не регистрируется автоматически** в текущем Harness/MCP. Для использования этих MCP-инструментов требуется добавить сервер в конфигурацию Harness или явно подключить в основном MCP. CLI `evidence_pipeline.py` уже работает напрямую, без этого шага.

## Консоль `pm.py`: доступность, флаги и подсказки

В host-режиме перед запуском агентов консоль перепроверяет TCP-порты из полного скана через
NetGuard задачи. Полный отрицательный результат останавливает запуск;
часть портов с `unchecked` не считается доказательством недоступности цели. Явный
`--force-unreachable` у `new`/`resume` разрешает продолжить после этой проверки.
Кэш полного скана старше 30 минут сопровождается предупреждением.
Порог можно задать через `PM_TCP_SCAN_STALE_MINUTES`.

Новый кандидат флага передаётся в сохраняемую очередь вопросов оператору.
Сохраняются точное значение, цель, источник, способ получения и доступные
материалы. Формат произвольный; можно предложить содержимое `user.txt`/`root.txt`
целиком. Пароль или токен без связи с заданием не предлагается как флаг.
Оператор самостоятельно отправляет значение на CTF-платформу и отвечает
«Да»/«Нет» в пункте «ВОПРОСЫ» либо через `questions TASK_ID --answer ID
--decision approve|decline`. «Да» выполняет связанную цель, «Нет» сохраняет
отказ и позволяет искать дальше. Просмотр и ответ работают при выключенной
цели, без модели, preflight, нового GET или обязательного VERIFY.
Независимые незавершённые цели могут исследоваться, пока ожидается ответ.
Отказ не предлагается повторно из-за нового result_id; явный пересмотр доступен
через `questions TASK_ID --reconsider PROPOSAL_ID --note-file PATH`.
Детали, миграция прежних подтверждений и ограничения —
[FLAG_CONFIRMATION.md](docs/FLAG_CONFIRMATION.md).

Текстовые шаблоны `PREFIX{...}`, `flag: ...` и параметры `--flag-pattern`,
`--flag-prefix`, `--flag-shape`, `--flag-expect` / `--flag-expect-file` помогают
обнаружению; они не ограничивают формат явно предложенного кандидата.
Общее совпадение `token=...`/`secret=...` само по себе не создаёт связанный вопрос.
Техническая проверка HTTP/loose Git-capture продолжает проверять целостность,
связь task/target и самогенерацию/отражение из запроса. Она описывает доказательство,
а принятие нового флага определяет явный ответ оператора. Отсутствие capture
не отменяет этот ответ. Повтор/readback не создаёт нового сетевого наблюдения.

`--hints-file PATH` у `new` и `intent` читает подсказки UTF-8 с переносами
строк. `--task-file PATH` (или `-` для stdin) передаёт большое задание без текста
в argv дочернего планировщика. Ограничение 6000 символов снято: явный предел
хранения UTF-8 — 16 MiB, превышение отклоняется без усечения. Большие материалы
передаются отдельными файлами и читаются диапазонами.

Coordinated: 15 решений координатора и 25 основных инструментальных шагов
специалиста; по исчерпании — сохранённый вопрос оператору ровно о +5. Учёт ведётся
по задаче/роли и не обнуляется новой сессией. До 15 запусков PoC на роль;
оправданный exec/PoC допускает до 600 секунд. Серии входа/путей имеют отдельные
внутренние единицы и критерии. См. [бюджеты и проверки](docs/RESEARCH_BUDGETS.md).

Причины остановки ролевого цикла: `iterations_done`, `flag_confirmed`,
`no_progress`, `stalled`, `state_unavailable`, `recon_failed`, `vuln_failed`,
`target_unreachable` (две итерации без новых наблюдений, все сетевые вызовы
завершились тайм-аутом или недоступностью), `goal_confirmed`,
`objectives_done`, `flags_without_goal`, `report_damaged`.
В coordinated-режиме повреждение/неполнота отчёта сохраняет паузу
`role_report_damaged_requires_review` / `role_report_incomplete_requires_review`.
Пауза и исчерпание бюджета не означают достижения цели.

Основная цель — текст ответа на вопрос «Что требуется сделать». Побочные
флаги-цели вводятся отдельным вопросом либо через повторяемый
`--objective "400:описание"` / `--objectives-file PATH` (одна позиция на
строку, `#` — комментарий). Вес от 1 до 10000; для основной цели действует
`--goal-weight N` (по умолчанию 100). В консоли побочные позиции разделяются
`;`, а `\;` означает буквальную точку с запятой в описании.

`--goal-first` (по умолчанию при заданных целях) и сохранённый `--goal-exclusive`
задают приоритет основной цели. Для ручного подтверждения задача завершается,
когда приняты все объявленные цели и достигнут сохранённый `expected_flags`;
основная цель не отменяет остальные. `--all-flags` сохраняет приоритет поиска
флагов. Без явного `--expect-flags` у задачи с целями ожидается один основной
флаг плюс число побочных позиций. Значение автоматически не уменьшается.
Один ответ связан с одной целью: одинаковые байты user/root требуют отдельных
подтверждений. После выполнения всех целей PM завершает задачу до следующего
модельного решения и проверки доступности. Старые подтверждения и их происхождение
сохраняются; историческая техническая отметка не становится ответом платформы.

## Ограничения

- Legacy Evidence Hub сохраняет метаданные Burp. Отдельный явный `pm_burp import` может сохранять приватные оригиналы запросов/ответов, включая query/cookies/auth; они не копируются в диагностические сводки и не смешиваются с браузерными пользователями. Границы описаны в [BROWSER_BURP.md](docs/BROWSER_BURP.md).
- Проверки Task Scope сохраняются в исходных Network Workflow и Burp importer.
- Аналитические вызовы Evidence Hub, координатор и восстановление формата используют runtime-политику `evidence_readonly.mjs`: она скрывает схемы и запрещает dispatch инструментов. Навязанный tool-call также отклоняет результат. Это проверяется установленным SDK с loopback fake API.
- Подтверждение HTTP ответа или открытого порта не равно подтверждению уязвимости.
- Для каждого запуска анализируется до 60 сетевых наблюдений и 50 последних Burp-записей; это ограничение размера контекста, а не полный исторический отчёт.
- Все производственные модельные обращения проходят через `orchestrator/model_adapter.py`: планирование, координатор, специалисты, форматирование и вспомогательный/legacy-анализ. Адаптер использует установленный Harness; самостоятельного HTTP-клиента модели в PM нет. Анализ принудительно отключает инструменты, исполнение требует явной политики.
- JSON-решение координатора проверяет action, role/profile, question, boundaries, inputs/references и expected_result. Границы ссылаются на сохранённое задание и известные ресурсы текущей задачи. Они не предоставляют новых разрешений: scope, NetGuard и бюджеты по-прежнему проверяет PM/исполнитель. Отдельное одобрение каждого ACCESS не требуется. Неизвестный ресурс или ссылка отклоняются до запуска роли.
- Каждый запрос имеет PM request_id, Harness session_id, runtime message ID при полученном ответе, статистику и связь с диагностическим run_id. Финальный текст ответа (без reasoning) хранится отдельно с правами 0600 и контрольной суммой: при диагностическом запуске — в `storage/run_events/model_requests`, вне него — в `storage/model_requests`; в событиях — фактические ссылки и причины отклонения. При восстановлении формата инструменты отключены; выполненный ход специалиста не запускается повторно из-за обрезанного отчёта.
- SDK rc2 не предоставляет отмену отдельной сессии. Тайм-аут/отмена закрывают принадлежащий адаптеру runtime; неизвестный исход операции требует рассмотрения, а не автоматического повтора. Результаты проверки subagents/workflow и прототипа двух специалистов описаны в [HARNESS_CAPABILITIES.md](docs/HARNESS_CAPABILITIES.md).
- Проверка противоречий ограничена точными структурированными конфликтами и явными формулировками доступа; произвольная проза не становится фактом. Ответы сервера учитываются по отдельным операциям, а не по наличию слова denied во всём выводе.

## Offline-проверки разработки

```bash
.venv/bin/python -m orchestrator.check_environment
.venv/bin/python tests/run_offline.py
.venv/bin/python tests/run_offline.py --runtime
.venv/bin/python tests/run_offline.py --list
.venv/bin/python tests/run_offline.py --runtime --only test_final_audit test_final_audit_runtime --verbose
```

`test_final_audit` выполняет обе self-test с временными путями под guard;
`test_final_audit_runtime` проходит настоящий первоначальный planner/PM/SQLite/
Harness/MCP через локальный API и HTTP: разведка → ACCESS → успех третьей пары →
отказ кандидата → другой кандидат → выключение → принятие → завершение без
лишних API/GET. Это не проверка настоящего VPN/root-broker или платного провайдера.

Каждый набор запускается в свежем процессе, с корнем фактического checkout.
Legacy assert-скрипты выполняются явно. Ошибки и пропуски выбранных тестов дают
ненулевой статус; тесты платного API и рабочей инфраструктуры перечисляются как
NOT RUN. `--runtime` добавляет только SDK/MCP с loopback fake API и временными
данными, без GLM, CTF-целей и sudo. В старой папке есть ручные скрипты с действиями
при импорте: общий `unittest discover` не является безопасной командой запуска.
Runner дополнительно запрещает Python-доступ к рабочему storage и считает
попытку нарушением даже при перехваченном исключении. Инцидент, из-за которого
добавлена эта защита, и ограничения описаны в [NETWORK_RESEARCH.md](docs/NETWORK_RESEARCH.md).

Разработка не изменяет рабочие задачи, SQLite и доказательства; миграции
проверяются на временных БД/копиях. Команды, обращающиеся к настоящим целям или
платному API, требуют отдельного задания. Требования автоматического ACCESS,
сохранения полезных сессий, параллельных направлений, условий комнаты и запрета
смены паролей описаны с текущими ограничениями в плане переработки.
CLI создаёт диагностический журнал даже для `--help`; проверки CLI при
разработке должны использовать временный `diagnostics.EVENT_DIR`, как фикстуры тестов.


### Конкурентные специалисты coordinated

Coordinated new/resume/attack запускают до двух специалистов одновременно через
единый адаптер Harness. `--max-specialists 1..10` сохраняет предел задачи.
Профиль не расширяет scope или инструменты; PM владеет общей памятью и целями.
Веб-специалист публикует проверенные по сохранённому источнику кандидаты через
pm_publish_candidate, ACCESS может проверять их параллельно. Кандидат, принятое
сервером значение и доступ различаются. Бюджет task/role не обнуляется профилем.
`.venv/bin/python pm.py specialists 1 --json` показывает шаги/session IDs;
`.venv/bin/python pm.py specialists 1 --cancel 42` запрашивает отмену конкретного шага.
Saved session ID не доказывает живость; прерванные действия не повторяются.

[Контракт, CLI, реальный SDK/MCP/HTTP/SSH smoke и ограничения](docs/SPECIALIST_WORKFLOW.md).
В rc2 нет доступного native workflow/subagent API: используется проверенный
owned-runtime механизм за общим адаптером. Orca и новые зависимости не добавлены.

### Библиотека успешных методов

`pm.py methods` хранит версионируемые обобщённые процедуры отдельно от памяти
задачи. Сохранение требует успешного действия и локальной проверки его оригинала;
summary или подтверждённый флаг не подтверждают остальные попытки. Релевантные
процедуры выбираются по профилю и конкретному вопросу для полного/сжатого контекста.
`methods save` и `methods retain` — явный выбор оператора, без модели, сети,
миграций task DB или удаления истории. [Формат, команды и ограничения](docs/METHOD_LIBRARY.md).

### Обычный вывод и ввод coordinated

По умолчанию PM показывает цель/следующее действие, фактический исход, новые
сведения, вопросы с ID и путь к полным результатам. `--diagnostic` включает
подробные EVENT/ID; JSONL сохраняется в обоих режимах. При TTY во время coordinated
можно вводить `вопросы`, `да ID`, `нет ID`, `статус`, `выход`; вывод специалистов
перерисовывает набранную строку. Ответ по флагу означает проверку на платформе,
не новый GET. Выход останавливает owned модельные runtimes, сохраняет паузу и
неизвестные исходы; сетевые правила удаляются отдельно.
[Интерфейс, различение исходов и реальные PTY/SDK/MCP проверки](docs/OPERATOR_CONSOLE.md).
