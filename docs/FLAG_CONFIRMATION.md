# Ручное подтверждение флагов

Реализовано от `b8d0a90`. Код: [flag_review.py](../orchestrator/flag_review.py),
[operator_questions.py](../orchestrator/operator_questions.py).
Разработка и миграционные проверки используют только временные SQLite и материалы.

## Путь кандидата

1. Специалист сохраняет `flags`: точное `value`, `source`, `method`, `path`,
   `objective_key`, доступные `goal_evidence`/`probe_result_id`/`artifact_ref`.
   Ссылка на материал полезна, но не обязательна для ответа оператора. Источник,
   сообщённый агентом без материала, остаётся заявленным, не проверенным.
2. PM связывает кандидат с текущими task/target и конкретной сохранённой целью.
   Известный путь `user.txt`/`root.txt` помогает выбрать соответствующую цель.
   Неоднозначное соответствие нескольких целей не угадывается. Специалист должен
   указать существующий `objective_key`. Без явных целей сохраняется связь с
   флаговым заданием; один только пароль/токен не создаёт флаговую цель.
3. В очередь автоматически добавляется `flag_confirmation`. Консоль показывает
   ID вопроса и кандидата, цель, точное значение в JSON-строке с экранированием
   переносов/управляющих символов, источник, способ и ссылки на материалы.
   Оператор самостоятельно проверяет значение на CTF-платформе.
4. «Да» (`approve`) атомарно сохраняет ответ и операторское происхождение,
   принимает кандидат для одной цели и подтверждает эту цель. «Нет» (`decline`)
   отклоняет кандидат, сохраняет причину, оставляет цель открытой и поиск возможным.
   `information` не заменяет решение о принятии флага.
5. Когда приняты все объявленные цели и достигнуто сохранённое ожидаемое число,
   PM завершает задачу до следующего решения модели, preflight или восстановления
   namespace. Закрытие задачи/уборка остаются отдельными действиями оператора.

Значение хранится без strip/regex-нормализации, включая переносы и пробелы.
Весь текст `user.txt`/`root.txt` допустим независимо от формата. Дополнительно
PM программно распознаёт уже сохранённый успешный одиночный `cat` такого файла
через argv и предлагает весь stdout без нового исполнения. Смешанный вывод
SSH/сессии требует явно оформленного кандидата; универсального парсера нет.
`token=...`/`secret=...` из общего regex-поиска без предметной привязки не создаёт
вопрос автоматически. Разбор испорченного/неполного отчёта не публикует кандидатов.

## Независимость от сети и доказательств

Ответ не вызывает модель или инструмент. Выключенная машина, закрытый scope,
отсутствие старого capture, неизвестный формат, SSH/shell-транспорт и отсутствие
VERIFY не мешают принятию ответа. Никаких требований двух выполнений, нового
GET или отдельного модельного аудита нет. PM не интегрирован с API CTF-платформы;
сохранённый ответ означает явное решение оператора после его проверки.

Локальный HTTP/loose Git-валидатор продолжает проверять байты, хэш, task/target,
связь result_id/artifact и отражение значения из запроса. Это технические сведения
о происхождении, а не автоматическое принятие нового флага платформой.
Исходные stdout/capture/отчёты сохраняются, недостающие материалы не придумываются.
Технический аудит SSH/shell как HTTP-capture не реализован; явное подтверждение
оператора применимо и к этим источникам.

## Ожидание, отказ и пересмотр

Ожидание не опрашивает модель. Если есть другая незавершённая цель без кандидата,
координатор может выбрать полезную проверку в существующих бюджетах. Если все
оставшиеся цели ожидают платформенного решения, сохраняется пауза. Просмотр
после перезапуска читает её без сети/API/ключа и без повторения завершённых шагов.
Полноценный параллельный workflow этим изменением не добавлен.

Идентичность кандидата: task, target, цель и точные байты значения. Новый
result_id, новый отчёт или readback не отменяет отказ. Другой источник добавляется
к материалам без повторного вопроса. Для того же отклонённого значения доступен
явный пересмотр с причиной; автоматического определения «новых обстоятельств»
по произвольному тексту нет. Пересмотр создаёт новую ревизию и вопрос; прежний
ответ и событие отказа сохраняются.

```bash
python3 pm.py questions 1
python3 pm.py questions 1 --answer 3 --decision approve
python3 pm.py questions 1 --answer 4 --decision decline --note-file /tmp/platform-response.txt
python3 pm.py questions 1 --reconsider 2 --note-file /tmp/reconsider-reason.txt
python3 pm.py resume 1
```

Числа в примере иллюстративные: CLI показывает реальные ID вопроса и кандидата.
В меню «ВОПРОСЫ» доступны ответы «Да»/«Нет»; пересмотр выполняется CLI.
Параметры ответа и пересмотра нельзя совмещать в одной команде.

## SQLite, память и прежняя история

Добавочная идемпотентная схема находится в прежней БД:

- `pm_flag_review_policy` — сохранённое ожидаемое число и неизменяемый снимок
  прежних подтверждений с исходным происхождением;
- `pm_flag_proposals` — точное значение/хэш, task/target, цель, источники,
  материалы, статус, ревизия и question_id;
- `pm_flag_proposal_events` — предложение, отказ, принятие, пересмотр и связывание
  прежнего ответа. Ответы также остаются в обычной очереди вопросов и её событиях.

В памяти публикуются `flag_proposal:ID`, их статусы, ответы, источники и цели.
Ответ, обновление цели, реестра флагов и памяти применяются одной транзакцией.
Фиксированный лимит старых отчётов не удаляет уже зарегистрированный кандидат.
Уменьшение `--expect-flags` при следующем запуске не снижает сохранённый минимум.
Одинаковые значения для user/root требуют двух отдельных ответов; одно принятие
не закрывает обе цели.

Прежние confirmed-строки и исходные отчёты не переписываются задним числом.
Исторические операторские подтверждения учитываются с сохранённой привязкой;
однозначный старый ответ связывается с целью без новой отправки. Неоднозначная
история требует предметного подтверждения. Историческая автоматическая отметка
HTTP/Git сохраняет свой статус/происхождение в реестре, но текущий вид цели
отмечает ожидание оператора; она не выдаётся за прежний ответ CTF-платформы.

## Проверки

[test_manual_flags.py](../tests/test_manual_flags.py) проверяет неизвестный формат,
отсутствие capture, выключенную цель/закрытый scope, user/root и ожидаемое число,
отказ/readback, пересмотр, старую историю, атомарный rollback, настоящий сохранённый
вывод публичного MCP-инструмента, read-only перезапуск и завершение без модели.
[test_http_capture_mcp.py](../tests/test_http_capture_mcp.py) проходит зарегистрированный
инструмент → подменённый broker → настоящее хранилище → вопрос/ответ → цель.
[test_coordinator_checkpoints.py](../tests/test_coordinator_checkpoints.py) сохраняет
автономную цепочку без ACCESS/significant gate. Реальная цель и API не проверялись.
