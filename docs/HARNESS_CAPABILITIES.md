# Harness: адаптер и локальная проверка возможностей

Проверено 14.11.2026 на checkout `fbeef2d` с текущими изменениями, Python 3.14.8.
Это проверка установленного runtime, а не обещание API будущих версий.
SDK не обновлялся. Совместимый набор закреплён в [requirements.txt](../requirements.txt):
`deepseek-harness-sdk==0.2.1rc2`, `deepseek-harness-runtime-bin==0.2.1rc2`,
`mcp==1.26.0`, `pydantic==2.14.2`.

## Общий путь вызова — реализовано

[model_adapter.py](../orchestrator/model_adapter.py) — единственное место создания
производственного `DeepSeekHarness`. Прямой HTTP к модели удалён из planner и
старого scheduler. Остальные клиенты также перенесены на адаптер:

| Клиенты | Политика |
|---|---|
| planner, coordinated_attack, evidence_pipeline, decision_agent, scheduler | analysis |
| agent_actions и его восстановление отчёта | execute; форматирование в новой analysis-сессии |
| lab_end_to_end | analysis сохранённых наблюдений |
| network_phase | execute с явной политикой; прежний MCP plan-only контракт сохранён |
| scheduler_harness | execute только RECON-demo; прочие роли и исправление формата — отдельные analysis-сессии |

У analysis последний overlay — проверенный `evidence_readonly.mjs`: скрывает
tool schemas и запрещает dispatch, включая навязанный вызов. Результат с tool
event отбрасывается целиком. Execute требует явной политики; ограничения
инструментов не заменяют scope/NetGuard и разрешения сохранённого задания.

Конфигурация объединяется в адаптере: общие defaults → параметры клиента
(например, бюджет роли) → явный `configuration(...)` текущего контекста.
Это один провайдер, без цепочки запасных. Адрес и плагины провайдера по-прежнему
задаются выбранным Harness-профилем; `base_url` — публичный SDK override.
Ключ передаётся SDK в памяти/окружении дочернего процесса, без argv/SQLite/событий.
В raw-артефакте маскируется точное значение переданного ключа; raw содержит
потенциально чувствительные данные задачи и требует обычной защиты storage.

`ModelResult` сохраняет SDK finish_reason/events/notifications и единые metadata:
PM request_id, session_id, runtime_message_id при наличии inbox receipt,
run_id, mode, recovery_attempt (0 — первый запрос), duration_seconds, счётчики
input/output/cache и peak_context_tokens. Максимальный контекст не суммируется
как расход токенов. Финальный текст без reasoning сохраняется в приватном raw;
JSON метаданных содержит SHA-256 и ссылку. Отклонение добавляет безопасную
rejection_reason; SQLite координатора сохраняет номер попытки и ссылку на raw.
События не дублируют текст модели или инструментов.

Адаптер сам не повторяет запрос. Существующие ограниченные восстановления
остаются у PM: одна попытка форматирования роли, бюджет decision_retries
координатора, существующие бюджеты аналитических путей. Повтор форматирования
происходит без инструментов, на сохранённых данных. После выполненных действий
max-tokens не продолжает action-enabled сессию; сохраняется исход операции и
форматируется отчёт. Новая исполнительная попытка допустима только при
доказанном отсутствии вызовов/результатов прежнего хода.

Исключения имеют безопасный код (`transport_error`, `timeout`, `cancelled`,
`configuration_or_start_failure`, `audit_error`, `shutdown_error`) и request_id;
исходное исключение остаётся в памяти. Терминальный finish_reason SDK остаётся
отдельным исходом модели. Ошибка записи явно предупреждает; при исходной ошибке
она не заменяет её. Частичная запись `status=running` после аварии не считается
успехом. Внутренние транспортные retries самого runtime могут существовать;
адаптер не добавляет автоматического повторного исполнения инструментов.

## Схема решения — реализовано

Валидатор [parse_decision](../orchestrator/coordinated_attack.py) требует точные поля:

```json
{
  "action": "run_role",
  "role": "vuln",
  "profile": "vuln",
  "question": "Проверить конкретное утверждение по сохранённому ответу",
  "reason": "Есть сохранённое доказательство для локального анализа",
  "boundaries": {
    "task_id": 11,
    "target": "10.0.0.1",
    "intent_ref": "intent",
    "resource_refs": ["service:10.0.0.1:tcp:22"]
  },
  "references": ["intent"],
  "inputs": [{"reference": "intent"}],
  "expected_result": "Цитата исходного результата либо явная неопределённость",
  "stop_kind": null
}
```

Task/target/intent_ref проверяются по сохранённому состоянию. Resource refs —
подмножество опубликованных PM `known_resources`, references/inputs разрешаются
заново перед исполнением. Неизвестные адреса, сервисы, профили, лишние полномочия
и ссылки отклоняются явно. Эффективные бюджеты вычисляет backend, не модель.
Границы и исходное задание сохраняются в полном и сжатом промптах специалиста.

Scope/NetGuard остаются исполнительной границей. Эта схема не является новым
универсальным анализатором shell-команд и не доказывает запрет любого обхода
через произвольный PoC/SSH; проверяемое сужение ресурсов внутри таких команд —
отдельный этап контроля исполнения. Старые завершённые шаги не мигрируются.
Старое planned-решение без новых полей безопасно отклоняется как
`invalid_saved_transition`, без автоматического исполнения или изменения прав.

В следующем изменении система инструкций вынесена в
[instructions/](../instructions/README.md). Поле profile теперь принимает
зарегистрированную специализацию, совместимую с ролью, а не только имя роли.
Набор разрешённых инструментов сужается runtime-политикой; бюджет пересекается
с исходным. Новый smoke-тест проверяет скрытие инструментов и отказ до MCP при
навязанном вызове. Это не добавляет роли новых прав или native workflow.

## Subagents/workflow — исследовано и проверено прототипом

В Python SDK доступны `start_session`, `resume_session`, `run`, notifications
callback и `close`. Отдельных публичных `subagents`, `workflow` и session-cancel
методов нет. В поставляемом бинарнике найдены реализации SubagentRuntime и
workflow-плагинов, но наличие кода не означает включение в нашем профиле.

В реальном `sdk-minimal` с PM MCP временный plugin проверил сервисы через
`agent.ctx.get`: `subagents` и `workflow` отсутствуют. Соответствующих инструментов
также нет в schema, полученной fake API. SDK runtime RPC не предоставляет
session/cancel; возможности отдельного ACP/CLI-протокола не подменяют SDK API.

[test_two_owned_specialists_events_mcp_and_independent_cancel](../tests/test_model_adapter_runtime.py)
создаёт два настоящих SDK runtime с отдельными сессиями. Пока один специалист
ожидает loopback-ответ, он отменяется закрытием его runtime. Второй продолжает
работу, вызывает реальный PM MCP `pm_capability_read` по stdio, получает ответ
в SDK, отдаёт результат. События и MCP stdout проверяются. Это прототип для
этапа 15, не внедрение параллельного координатора и не штатный native workflow.

Для этапа 15 пригодны owned runtime на направление, SDK notifications,
сохранённые session_id и MCP stdio. Одна отмена общего runtime затронула бы все
его сессии; до появления проверенного публичного cancel API отменяемые
направления следует разделять по runtime. Родство направлений, общую память,
общие бюджеты, блокировки и operator checkpoints должен хранить PM.
`resume_session` присутствует, но сохранение полезных живых сессий после
перезапуска этим прототипом не проверено и в PM ещё не внедрено. Подключение
native workflow потребует отдельной проверки профиля и контракта SDK, без
Orca и без переписывания PM на Cordis.

## Воспроизводимые проверки

```bash
.venv/bin/python -m orchestrator.check_environment
.venv/bin/python tests/run_offline.py
.venv/bin/python tests/run_offline.py --runtime --only test_model_adapter_runtime test_coordinated_runtime test_evidence_readonly_runtime
```

Environment check только читает версии, файлы и публичные сигнатуры; не
запускает runtime/модель, не читает ключ, не открывает БД. Непроверенная версия
возвращает ненулевой статус, а не молча считается совместимой.

Этап памяти от `9b275d9` отделяет стабильную часть PM-промпта маркером
`<pm_dynamic_context>`, фиксирует её SHA/размер и полный размер запроса.
SDK не предоставляет публичного cache_control: неизвестные API-параметры не
добавлялись. Учитываются только SDK-reported input/output/cache-read; отсутствующие
метрики и неполные итоги — null. Положительный cache counter отмечает наблюдённый
hit; loopback fake usage проверяет обработку, не production-экономию.
[TASK_MEMORY.md](TASK_MEMORY.md) содержит измерение байтов и ограничения.

Новые шесть runtime-тестов используют настоящий установленный SDK, MCP-клиент,
session.run и production FastMCP stdio. Заменены API модели (loopback SSE),
рабочие данные/конфигурация (временные каталоги), привилегированный executor
(разрешён только пустой session list, целевой dispatch запрещён). Проверены
планировщик, вспомогательный анализ, актуальный контекст координатора,
невалидное решение/исчерпание восстановления, фактическое поручение роли,
MCP readback, успешное форматирование, навязанный tool-call в восстановлении,
отмена/тайм-аут/ошибка транспорта и отсутствие повторного MCP-исполнения.
Прежние три SDK/MCP smoke-теста также проходят.

Внешний провайдер, CTF-машина, sudo, реальные SSH/PoC, native subagent workflow,
постоянные параллельные направления и восстановление сессий не проверялись.
В прежнем прямом SDK read-only smoke виден ResourceWarning о незакрытых pipe
объектах SDK rc2 при успешном shutdown. SDK не обновлялся ради подавления warning;
обновление требует отдельного прогона совместимости. При sandbox-запрете
loopback нужны разрешённые локальные сокеты; пропуск не считается прохождением.


## Этап 15: применение проверенного прототипа

На базе `1de9fd0` внедрён [owned specialist workflow](SPECIALIST_WORKFLOW.md)
за тем же model_adapter. Нативные subagents/workflow/session-cancel в rc2
по-прежнему недоступны; зависимости не обновлялись. PM хранит исследование,
адаптер управляет отдельными настоящими runtime через публичные SDK методы.
Четыре [новых runtime-регрессии](../tests/test_specialist_workflow_runtime.py)
проверяют конкурентные PM роли, MCP stdio, локальные HTTP и настоящий OpenSSH,
независимую отмену и завершение по целям. Приведённые выше ограничения этапа 2
относятся к его прототипу; актуальное покрытие и замены описаны в новом документе.
