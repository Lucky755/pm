# Библиотека успешных методов

Реализовано на базе `864e26edb61857c70714b4ee65a383cdf55571e1`, 17.11.2026.
Библиотека отделена от [памяти задачи](TASK_MEMORY.md) и статических
[instructions/procedures](../instructions/procedures). PM не меняет свои исходники
и общие инструкции во время исследования.

## Где хранится и кто изменяет

По умолчанию — приватный `storage/method_library/catalog.json`; для временного
окружения есть `PM_METHOD_LIBRARY_DIR`. Чтение пустой библиотеки не создаёт каталог.
Новой SQL-базы всех машин и миграций task DB нет. Запись выполняет только явная
операторская CLI-команда. У агентов нет MCP-инструмента записи библиотеки.

Каталог содержит schema version и последовательные версии каждой процедуры.
Writer использует flock, временный файл, fsync и атомарную замену. Для изменения
процедуры нужны ожидаемая версия и причина; конфликт не затирает другую запись.
Старые версии, происхождение и отозванные процедуры сохраняются. Изменённый
совет получает только повторно проверенное основание этой версии; прежние
основания сохраняются в прежних версиях. Повреждённый
каталог выдаёт явную ошибку, не заменяется пустым файлом. Предел каталога 16 MiB
проверяется до публикации, без усечения.

## Запись и проверяемый успех

В документе для `methods save` два поля: `method` и `evidence`.
`method` содержит:

| Поле | Содержание |
|---|---|
| key | стабильный ключ метода; сохраняется при исправлениях |
| title | краткое название |
| profiles | применимые зарегистрированные профили PM |
| problem_tags | отдельные слова для выбора по текущему вопросу |
| conditions | необходимые условия применимости |
| method | ограниченная последовательность полезных действий с параметрами вместо данных машины |
| tools | зарегистрированные PM-интерфейсы, нужные методу; зависимости утилит описываются в conditions/limitations |
| limitations | границы доказанного результата и технические ограничения |
| not_applicable | причины не применять процедуру |

`observed_result`, версия, происхождение и сведения о проверке добавляются
производственным валидатором, не берутся из summary модели.

Поддержаны три узких вида `evidence`:

- **http_response**: result_id исходного capture, artifact_ref и точная quote.
  Проверяются запись действия, task/текущий target/scope, оригинальный артефакт,
  целостность/полнота, цитата, успешный HTTP-статус и отсутствие отражения цитаты
  из запроса. Loose Git blob проходит прежнюю проверку формата/длины/хэша.
  Доказано получение этих байтов; это не автоматически рабочий логин/доступ.
- **http_criterion**: дополнительно series_id зарегистрированного pm_check_series.
  Действие, сохранённая серия и оригинальный exchange/capture должны совпасть.
  Критерий find_file/authenticated повторно проверяется локально по оригинальным
  байтам и квитанции. HTTP 200 сам по себе недостаточен. Успех authentication
  означает выполненный критерий принятия данных, не shell-доступ. Inventory без
  решающего критерия не принимается как успешная целевая проверка.
- **material_transform**: result_id настоящего pm_material_process, ссылка на
  полученный материал и точная quote. Проверяются квитанция преобразования,
  запись обработчика, выходные байты/хэш/полнота и цепочка исходника. stderr не
  является результатом анализа. Успешное преобразование не подтверждает любую
  интерпретацию содержимого или полный захват прежнего источника; неизвестная
  полнота приобретения остаётся null.

Новый метод требует нужного поддержанного интерфейса в tools. Произвольный stdout
PoC/SSH, summary, заметка, readback, ошибка/тайм-аут или один принятый оператором
флаг не проходят вместо этих квитанций. Флаг не подтверждает все предыдущие
действия. Для иных типов успешных операций нужен отдельный проверяемый контракт;
они не объявляются уже поддержанными.

Происхождение хранит task ID, хэш локальной идентичности задачи, result_id,
artifact_ref, хэши записи действия и исходных байтов, время и версию валидатора.
Полный журнал, stdout, цитата и тело ответа в каталог не копируются. Повторное
чтение той же исходной записи не становится новым происхождением. Новый result_id
кэшированной серии не увеличивает число успешных выполнений.

## Дубликаты, исправления и секреты

Стабильный key объединяет исправления, нормализованное содержимое объединяет
одинаковые процедуры с разными заголовками/ключами. Для нового проверенного
источника дополняется происхождение существующей записи. Это точная
нормализация, не универсальная семантическая дедупликация произвольного текста.
Исправление требует `--expected-version` и осмысленную `--reason`; исходный успех
проверяется повторно локально. `withdraw` отзывает применимость, сохраняет историю
и исключает процедуру из следующих промптов. Самопроизвольного возврата нет.

Значения известных флагов и кандидатов, учётных данных памяти, сохранённых
HTTP auth/cookies и пар из серий, буквальный текущий target, известные форматы
ключей/флагов и копирование исходной цитаты блокируют экспорт в совет. Вместо
секретов и адресов нужны параметры, например `{{credential}}` и `{{resource}}`.
Проверка не является универсальной деклассификацией произвольного текста:
необозначенный контекстный секрет может не иметь распознаваемой структуры.
Оператор выбирает обобщённую процедуру; сырые материалы не добавляются в советы
автоматически. Материал цели не может добавить поля scope/system_prompt или
расширить инструменты/разрешения. Все прежние runtime guards сохраняются.

## Релевантный контекст

Сборщик полного и сжатого промптов включает одинаковый отдельный method_library
блок внутри изменяемых данных. Выбор требует одновременно зарегистрированный
профиль, совпадение problem_tags со словами конкретного задания и доступность
нужных PM-интерфейсов. Действующие ограничения, в том числе offline, пересекаются
с инструментами профиля. Выбор детерминированный: до трёх процедур, с числом
совпадений и пропущенных записей. Никакого модельного запроса для выбора нет.

В prompt попадают обобщённые условия/метод/ограничения и узкий observed_result;
история старых машин и исходные материалы не передаются. Это справочные данные,
не факты текущей задачи, не новые инструкции и не разрешение на повтор операции.
Профиль веб-агента не получает бинарную процедуру только по наличию в библиотеке.
Материалы не запускают tools и не меняют общие инструкции или исходники.

## Явные команды сохранения

```bash
.venv/bin/python pm.py methods list
.venv/bin/python pm.py methods select --profile http-surface --problem 'Audit HTTP capture'
.venv/bin/python pm.py methods save 1 --file selected-method.json
.venv/bin/python pm.py methods retain 1 --file selected-materials.json
```

Последние две команды — операторские примеры, разработчик их на задаче 1 не
выполнял. Save-документ имеет форму (идентификаторы нужно выбрать из своей истории):

```json
{
  "method": {
    "key": "audit-saved-http",
    "title": "Локальная проверка оригинального HTTP-ответа",
    "profiles": ["verify"],
    "problem_tags": ["http", "capture"],
    "conditions": "Сохранены оригинал и его квитанция.",
    "method": ["Проверить принадлежность оригинала задаче и целостность.", "Сослаться на точные исходные байты."],
    "tools": ["pm_http_capture"],
    "limitations": ["Получение байтов не доказывает доступ."],
    "not_applicable": ["Оригинал отсутствует или повреждён."]
  },
  "evidence": {
    "kind": "http_response",
    "result_id": "ORIGINAL_RESULT_ID",
    "artifact_ref": "http_artifact:ID",
    "quote": "EXACT_QUOTE"
  }
}
```

Для исправления save использует прежний key, `--expected-version N --reason TEXT`.
`methods show METHOD_ID --version N` читает конкретную версию;
`methods withdraw METHOD_ID --expected-version N --reason TEXT` отзывает её.
Save/retain открывают task DB в SQLite mode=ro: не вызывают pm.connect,
инициализацию, модель, broker или сеть.

После завершения консоль предлагает явное сохранение. Retain-manifest содержит
только выбранные ссылки и IDs:

```json
{"materials": ["http_artifact:ID", "file_material:ID"], "methods": ["method:ID"]}
```

Сохраняются выбранные оригинальные байты HTTP-body/файла и версии советов.
Приватные blobs лежат отдельно в retained-originals, с хэшами и размерами в
manifest. Они могут содержать секреты, **не подмешиваются в промпты библиотеки**
и не становятся советами. Это не полный перенос task DB/HTTP wire/session bundle.
Исходная рабочая история, квитанции и доказательства не удаляются. Retain можно
выполнить и для неполного исследования; это не объявляет его успешным.

## Проверки

[15 offline-контрактов](../tests/test_method_library.py): успех, отсутствие записей
за summary/PoC/readback, принятый флаг и посторонняя попытка, дубликаты/происхождение,
версии/CAS/конкурирующие writers, отзыв, повреждённые/чужие/неполные исходники,
секреты, реальный сборщик обоих промптов и run_role с подменённой моделью,
read-only CLI и явно выбранные оригиналы без удаления истории.

[4 runtime-теста](../tests/test_method_library_runtime.py): настоящие
зарегистрированные MCP-функции, HTTP worker и loopback-сервер, ограниченная серия,
Basic auth, реальное преобразование UTF-16. Заменена только привилегированная
gраница broker/namespace; библиотека не вызывает executor. Отдельно проверяется
кэшированный wrapper без нового происхождения и отсутствие повторной сети.
Этот набор не выдаётся за проверку нового модельного SDK-пути; прежние SDK/MCP
регрессии выполняются полным runner. CTF/VPN, платный API и sudo не используются.

```bash
.venv/bin/python tests/run_offline.py --only test_method_library
.venv/bin/python tests/run_offline.py --runtime --only test_method_library_runtime
```
