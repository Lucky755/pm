# Обнаружение портов, доступность и сервисы

Реализовано от `1b9d7c9`. Это разные сведения:

- **Discovery** — наблюдаемое состояние порта, протокол, время, исходный run /
  observation ID. Открытый порт не устанавливает продукт.
- **Availability** — отдельная TCP-проверка текущего соединения. Предыдущее
  обнаружение не гарантирует текущую доступность. Чтение старого результата
  сохраняет прежнее время наблюдения.
- **Identification** — существующий `service_versions` / структурированные
  service probes. service_hint/version_hint сохраняют неопределённость;
  RECON/модель не повышают их до подтверждённого продукта по имени порта.

Официальная семантика состояний: [Nmap port states](https://nmap.org/book/man-port-scanning-basics.html),
[UDP responses](https://nmap.org/book/scan-methods-udp-scan.html).
PM различает open, closed, filtered, open|filtered, timeout и unchecked.
Timeout/unchecked относятся к исходу проверки, не являются доказательством
состояния удалённой машины. Два скана не гарантируют обнаружения всех сервисов.

## Очереди и сохранение

Полный TCP connect 1–65535 сохранён с прежним ограничением одной Nmap-операции
240 секунд. Он не превращён в бесконечный scan. Вывод/программная сводка и
порты сохраняются **до** follow-up. При тайм-ауте сохраняются частичный результат,
known open ports и исходный stdout. Partial/empty/completed не запускают новый
tcp_full при повторном входе. Неизвестный running требует отдельного разбора.
После частичного полного скана дальнейшее исследование — явная очередь портов;
молчание Nmap о конкретном порте не становится closed.

`survey` / `pm_port_survey` используют существующие network_phase_plans,
network_job_runs, network_observations. Отдельной несовместимой БД нет.
TCP: до **50** явных портов в операции; соответствующие проверки PM/MCP/
executor/broker согласованы. UDP: до 50 в очереди, по **8** в операции.
Параметр CLI max_jobs (1–8) ограничивает операции на вызов, по умолчанию одна.
MCP выполняет ровно одно новое задание на инструментальный шаг; max_jobs != 1
отклоняется, чтобы не расширять бюджет специалиста скрытым пакетом операций.
Операции завершаются и сохраняются по очереди; повторный вызов продолжает
только не начатые задания. Timeout/failed/running не повторяются автоматически.
Пересекающиеся завершённые наборы не создают повторных проверок. Для поднабора
чужого pending-набора требуется продолжить его сохранённые параметры явно.

Отдельный UDP-worker выполняется без root/CAP_NET_RAW в прежнем task NetGuard:
connected UDP socket, один байт `00`, тайм-аут **2 секунды на порт**. Ответ — open,
ECONNREFUSED — closed, молчание — open|filtered. Это ограниченное UDP-исследование,
не полная протокольная идентификация DNS/SNMP и не замена Nmap service probes.
Прежний привилегированный `nmap_udp` (-sU, ≤8 портов) остаётся отдельной поддержанной
операцией с CAP_NET_RAW. Произвольный root PoC не предоставляется.

Примеры для иллюстративной задачи №11, **не выполненные над рабочей задачей**:

```sh
.venv/bin/python pm.py survey 11 --protocol udp --ports 53,67,69,123,137,161 --max-jobs 1
.venv/bin/python pm.py survey 11 --protocol tcp --ports 22,80,443,8080 --max-jobs 1
```

Требуется обновлённый оператором root-owned broker. При разработке установленная
копия не обновлялась. Web/URL scope отвергает host survey до configure/пакетов;
URL-запуск не сканирует общий IP автоматически. Общая карта получает UDP и TCP
из того же проверенного сборщика: task/target/protocol/ports/result identity.
Проверенный partial-port сохраняет происхождение и общий исход run.
Полный инвентарь хранится целиком; ограниченный prompt отдельно сообщает пропуски.
`pm_port_status` читает сохранённые состояния/счётчики страницами, без сети.
Однотипные результаты суммируются Python/SQLite; модель нужна для интерпретации.

Preflight хранит текущую очередь в pm_port_preflight, историю — в прежних
pm_tcp_full_scan_attempts. Общего десятисекундного дедлайна больше нет: ≤50
портов за операцию, индивидуальный TCP timeout ≤2 сек, внешний timeout рассчитан
по размеру операции. Один вход проверяет не более восьми пакетов, остальные
остаются unchecked. Следующее явное продолжение берёт непроверенное;
истёкшая свежесть приводит к новой точечной проверке. Старое open не получает
новый last_seen_at только из-за чтения. Пока есть unchecked, недоступность всей
выборки не объявляется. Отсутствие ICMP/ping не считается выключением.

## Ошибки и выключенная машина

target-state хранится отдельно от scope/доказательств с историей и причиной:

- active — сетевые действия разрешены заданием; это не подтверждение живости;
- temporary_error — ошибка транспорта/протокола исполнения;
- services_unavailable — проверенные соединения не дали доступного сервиса,
  состояние питания хоста не установлено;
- confirmed_unavailable/deactivated — только явное утверждение оператора.

Негативный TCP-ответ closed не запрещает другие протоколы. Свежий сохранённый
UDP-ответ позволяет войти в координатор без повторного полного TCP-скана.
При неудаче preflight выполняется одна локальная проверка маршрута/интерфейса
через broker (`ip -j route get`, operstate), отдельно от уже проверенных портов.
Она не посылает ping/target packets, не восстанавливает VPN и не доказывает
доступность приложения. При неизвестном результате самой диагностики это явно
отмечается; исходный отказ не заменяется успешной диагностикой.

```sh
.venv/bin/python pm.py target-state 11 --state deactivated --reason "CTF platform: machine stopped"
.venv/bin/python pm.py resume 11 --coordinated --continue-coordinated
```

Offline resume обходит configure, namespace restore, скан и preflight.
Координатор выбирает saved-analysis: актуальное задание, saved refs и конкретный
локальный вопрос. Настоящий run_role и SDK-политика оставляют только чтение
материалов/память/заметки; MCP отдельно блокирует активные пути. После одного
полезного анализа текущего знания сохраняется маркер: без новых данных следующий
просмотр/продолжение не вызывает модель снова. Пауза показывает причину и что
свежие TCP/UDP/HTTP/SSH требуют восстановления. Работа старого ролевого цикла
сеть не обходит. Наличие старого capture не требуется для ответа на вопрос о
флаге; выполнение всех целей проверяется до новой модели.

После реального восстановления оператор явно задаёт target-state active.
Обычное «продолжить» и force-unreachable не снимают сохранённую остановку.
Существующие разрешения scope, room conditions, запрет смены паролей и защита
unknown outcomes сохраняются. Имеющиеся SSH-клиенты не уничтожаются этим
переключателем: он запрещает новые действия PM, не является kernel kill switch.
Автоматические повторные GET/сканы для подтверждения выключения отсутствуют.

## Проверки и ограничения

[test_port_research.py](../tests/test_port_research.py) проверяет реальные
loopback TCP open/closed/timeout и UDP reply/silence, UDP через публичный MCP и
настоящую SQLite-очередь, partial/timeout resume, пересечения, программные
сводки, URL denial, сохранение времени доказательств и отсутствие replay.
Offline-координатор и фактический prompt run_role проверяются с поддельной
моделью и запретом исполнителя/remote session reconciliation. Есть сценарий
принятия неизвестного флага без capture при выключенной цели.
Полный TCP/Nmap и broker namespace заменены только внешними границами в
соответствующих интеграционных тестах; настоящие VPN/nft/bubblewrap/привилегированная
диагностика не проверялись. Это не испытание рабочей цели/GLM.

### Инцидент изоляции при разработке

Новый offline-переход в старом test_full_scan_recovery дошёл до стандартного
agent_actions.DB_PATH: фикстура меняла pm.DB, но не все пути координатора.
До запроса ключа были выполнены служебные SQLite-обновления задачи №1.
Read-only осмотр обнаружил новую pm_memory_revisions #1 с причиной
coordinator_resume_reconcile от 2026-11-16T15:08:28.559907+00:00 и status=running
в pm_coordinator_runs #1 при прежнем stop_reason. Полный diff без исходной копии
не установлен.
Операторская очередь также содержит созданные в 15:08:28 UTC pending
flag proposal #1 и flag_confirmation question #1. В pm_flag_review_policy
expected_flags=2, тогда как сохранённая операторская цель имеет expected_flags=1.
Эти поля не исправлялись вручную без исходного снимка; требование не изменять
рабочую SQLite при разработке было нарушено этой тестовой ошибкой.

Сетевые/модельные вызовы и новые роли не выполнялись; исходные
отчёты и доказательства этим путём не перезаписывались. Исторические значения
не восстанавливались из предположений. Снимок **после** инцидента сохранён
read-only backup в `/tmp/pm-network-research-db-incident.sqlite3` (0600);
это не снимок для автоматического отката.

Фикстура исправлена, дополнительные старые обращения к working storage тоже
изолированы. Теперь каждый Python-процесс offline runner получает audit guard,
запрещающий доступ к checkout/storage до SQLite/open. Нарушение делает набор
неуспешным даже при перехваченном исключении. Тест защиты использует собственный
временный «рабочий» каталог; проверки не удалялись и не заменялись skip.
