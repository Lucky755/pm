# Операторская консоль: этап 17

Реализовано на базе `27aa5524a30bcaed2f320e19c4b515abbd34098e`, ветка main.
Одна Kali, один оператор, ручной процесс PM. Изменена подача информации;
PM по-прежнему владеет scope, целями, памятью, вопросами и бюджетами.

## Обычный и подробный вывод

Обычный режим показывает цель/направление, выбранный следующий шаг, действие,
краткий фактический исход, изменения доступа/публикацию кандидатов и пути к
сохранённым результатам. Сводка сохранённого отчёта не объявляет завершение роли
достижением цели. В обычный поток не попадают EVENT-записи, служебные dict/JSON,
токенные счётчики и повтор всей истории; в конце показываются последние шесть
шагов с числом более ранних записей и способом их просмотра.

```bash
.venv/bin/python pm.py attack 1 --coordinated
.venv/bin/python pm.py attack 1 --coordinated --diagnostic
.venv/bin/python pm.py specialists 1 --json
```

Это примеры интерфейса; разработчик не запускал рабочую задачу 1.
`--diagnostic` или `PM_DIAGNOSTIC=1` сохраняет подробный EVENT-вывод, IDs,
корреляцию и метаданные, в том числе через дочерние процессы. `--json` остаётся
явным машинным интерфейсом; прогресс coordinated направляется в stderr, а
возвращаемый JSON — в stdout. Сами JSONL-журналы сохраняются **в обоих режимах**.

Presentation использует существующую модель диагностических событий, не новую
БД/шину состояния. `ConciseProgress` сохраняет новые `[PM]`-сообщения и ограниченные
восстановления модели; частичные строки разных потоков собираются раздельно.
Существующие проверки подробного формата переведены на явный debug; assertions
о наличии полей/маскировке/корреляции сохранены. Обычный формат проверяется отдельно.

Различаются: исполненная операция, ненулевой exit_code, отказ до исполнения,
структурированный server_outcome=refused, неизвестный исход/тайм-аут, повреждённый
или неполный отчёт, исчерпанный бюджет, выключенная цель и ожидание оператора.
Слова denied/404 в произвольном stdout не классифицируют другие операции.
HTTP-статус показывается как наблюдаемый ответ, а не доказательство входа/цели.
Ошибка модели имеет свой статус и путь к аудиту; не превращается в ошибку сети
исполнителя. При ошибке доступен result_id/путь полного результата либо журнал.

## Ввод во время coordinated-запуска

При настоящих stdin/stdout TTY coordinated в new/resume/attack включает один
локальный читатель ввода. Он запускается **после** получения ключа и начальных
операторских решений, не конкурируя с getpass. Просмотр уже сохранённой паузы
не запускает этот цикл/модель и не запрашивает ключ. Действие в интерактивном меню
имеет свой run_id. Полезные независимые специалисты продолжают работу.

```text
pm [вопросы | да ID | нет ID | статус | выход] >
```

- `вопросы`/`questions`, `статус`/`status` показывают текущие вопросы.
- `да 12`/`yes 12`, `нет 12`/`no 12` отвечают только на выбранный ожидающий ID
  текущей задачи. Ответ без ID, чужой ID и повтор уже отвеченного не применяются.
- `выход`/`exit`/`quit`, EOF и Ctrl+C прекращают ручное исполнение.

Редактор использует stdlib termios/select, UTF-8 и Backspace. Полные строки
конкурентного вывода печатаются с блокировкой и перерисовкой текущего набора;
данные источников не поставляют управляющие последовательности. Это короткая
командная строка PM, не shell, SSH-терминал или полный readline с историей.
При перенаправленном вводе TTY-режим не включается; обычная CLI и отдельный
`questions --answer ID --decision approve|decline` остаются доступны.
Legacy-цикл сохраняет синхронный ввод и выход Ctrl+C; живые команды относятся
к coordinated-маршруту. Зависимая ветка ждёт по прежней очереди; UI не выдаёт
новых разрешений. Ошибка чтения очереди видна и сама не отменяет исследование.

## Вопрос и флаг

Вопрос содержит ID, причину, задачу/target/resource границы, зависимую ветку,
последствия Да/Нет и явный синтаксис ответа. Для tool/pivot показываются сведения
сохранённой квитанции. Ответ не расширяет scope или бюджет произвольным текстом;
бюджетный receipt добавляет только предусмотренные +5. Применение tool/pivot
использует прежние поддержанные операции, не выполняется самим читателем ввода.

Флаг показывается полностью: точное JSON-представление (включая whitespace и
управляющие байты), обычное копируемое значение для печатаемой строки, источник,
способ получения, материалы и конкретная цель. Для этого текста не применяется
общее маскирование `password=`/`token=`, которое могло бы испортить сам флаг.
Зарегистрированный API-ключ скрывается даже при ошибочном попадании в кандидат.
Да означает самостоятельную проверку оператором на CTF-платформе; Нет отклоняет
кандидата. Ответ выполняет существующий operator_questions.answer/flag_review,
не GET, preflight, VERIFY или новую модель. Выключенная цель этому не мешает.
При выполнении всех целей прежняя проверка завершает исследование до нового
решения. Ожидание в интерактивном меню сохраняется и не закрывает консоль.

## Остановка и полные данные

ExecutionControl за единым Harness-адаптером регистрирует runtime текущего ручного
запуска, включая координатор, специалистов и форматирование. Выход закрывает
именно эти owned runtimes; новая модель после запроса остановки запрещена.
Поддержанного native session-cancel в SDK rc2 нет: используется проверенный close.
Полезные SSH/PTY/маршруты задачи остаются у прежнего session manager; UI их не
закрывает и не удаляет NetGuard. Уже отправленная broker/удалённая операция может
иметь неизвестный исход; остановка модели не обещает откат команды на цели.

Начатые шаги сохраняют неизвестность, промежуточный отчёт — прерывание.
Координатор сохраняет waiting_operator/interrupted. Следующий обычный просмотр
паузы не делает модельных/сетевых действий. Явное продолжение не превращает
неизвестный исход в успех и не повторяет исполненное; спорная ветка сохраняет
прежнюю защиту до проверяемого разбора. В конце — причина, незавершённые действия
и путь JSONL. SIGKILL по-прежнему оставляет узнаваемые незакрытые START.
Удаление сетевых правил — отдельная явная операторская операция.

Типовые HTTP-серии журналируют отдельные check IDs со START/END и родительским
действием. Они больше не перекрывают action_id внешнего инструмента. Генерируемые
сотрудничающие PoC используют прежний PM_CHECK: подробные строки остаются в
исходном capability-артефакте, консоль показывает число начатых/завершённых проверок
и неполноту. Произвольный неинструментированный код не становится измеренным.
Сокращается только показ: допустимый полный stdout/capture/материал хранится
прежним способом, включая данные, не выданные модели. MCP stdout остаётся
JSONRPC; человекочитаемые события отображает родитель, предупреждения идут в stderr.

## Проверки

[11 offline-тестов](../tests/test_operator_console.py): обычный/debug формат,
различение исходов, точные флаги/секреты, явный ID, конкурентные частичные строки,
owned stop, PoC-сводки, выключенная цель/успех без cleanup и сохранение полного
140000-байтного результата при кратком показе. Модель/исполнитель там подменены.

[3 настоящих runtime-теста](../tests/test_operator_console_runtime.py):

1. Реальный PTY, одновременный WEB/ACCESS вывод и частично введённый `да ID`;
   ответ сохраняется в временной SQLite только у выбранного вопроса.
2. Реальный PTY и unknown-format флаг из сохранённого отчёта без capture:
   точное значение, явное принятие при deactivated, выполненная цель без модели/
   GET и восстановление terminal attributes после выхода.
3. Установленный Harness/session.run, настоящий MCP stdio и локальные HTTP/SSH
   из сценария этапа 15: выход при активных специалистах, остановка новых модельных
   запросов, сохранение неизвестных исходов и пауза без автоматического продолжения.

Для третьего теста заменены модельный API (loopback SSE) и граница broker/
namespace; SDK/MCP/TTY/OpenSSH не подменяются. Реальные CTF/VPN, платный API, sudo,
native workflow и произвольное принудительное прерывание PoC не проверялись.

```bash
.venv/bin/python tests/run_offline.py --only test_operator_console
.venv/bin/python tests/run_offline.py --runtime --only test_operator_console_runtime
.venv/bin/python tests/run_offline.py --runtime
```

Все тесты используют временные БД/артефакты/конфигурацию и storage guard.
Сокетные runtime требуют разрешённых локальных сокетов; запрет среды не считается
прохождением и не скрывается skip. Новых зависимостей или обновления SDK нет.
