# Автономность и вопросы оператору

Реализовано от `9cfce64`. PM выбирает и исполняет ACCESS без отдельного одобрения
каждого шага. Материалы, кандидаты учётных данных и сохранённый доступ используются
внутри исходного задания. Ни роль, ни профиль, ни модель не расширяют разрешения.
Одна попытка не превращается в перебор; ограничения комнаты остаются обязательными.

## Что больше не останавливает работу

`coordinator_checkpoints.BLOCKING=False`. Координатор не вызывает `collect`,
`pending` или `review` для принятия решения о продолжении. Классификатор можно
вызвать отдельно для описательных меток; его прежние pending/reviewed записи
сохраняются, но не являются разрешением, запретом или доказательством.
`significant()` оставлен только как совместимый описательный helper без вызовов
в цикле. Раскрытие Git/секрета и изменение доступа автоматически обновляют
состояние; обычные и нестандартные ответы интерпретирует специалист по исходным
байтам. Отсутствие фиксированной категории ответа не означает неполноту отчёта.

Сохраняются проверки JSON/схемы управления, ссылок, scope/NetGuard, бюджетов,
неизвестного исхода, повреждённого/противоречивого отчёта и триажа перед эскалацией.
Завершение роли не является достижением цели. Достаточные прежние доказательства
могут завершать цель без лишней модели; ожидание и исчерпание бюджета — не успех.

## Очередь

`pm_operator_questions` в существующей SQLite хранит ID, task/target, kind,
question, reason, boundaries, references, branch_id, step_id, status и answer.
`pm_operator_question_events` сохраняет запрос/ответ. Изменения атомарны; повторный
ответ на уже закрытый вопрос отклоняется. Оригиналы не перезаписываются.

Допустимы только вопросы:

- `pivoting` — другая цель/маршрут/scope;
- `tool` — получение/установка инструмента или предусмотренная документация;
- `budget` — расширение бюджета;
- `flag_confirmation` — решение по одному существующему `flag:...` reference.

В `wait_operator` требуется `operator_question={"kind":"..."}`. Все остальные
поля валидируемого решения остаются: конкретное задание, причина, границы, inputs,
references и ожидаемый результат. `branch_id` — `task` либо известный service
reference; для сервиса `boundaries.resource_refs` содержит только эту ветку.
Неизвестные ресурсы/ссылки, обход ожидающей ветки через task-wide границы и
повторный вопрос той же ожидающей ветке отклоняются до dispatch.

Вопрос по одному сервису позволяет координатору работать с другими сохранёнными
сервисами в пределах бюджета. При отсутствии доступной ветки модель не опрашивается.
После сохранённой паузы обычный просмотр не вызывает модель, preflight или
восстановление namespace. Явное продолжение полезной независимой работы возможно
через `--continue-coordinated`; оно не отвечает на вопрос автоматически.
Фактическая полезность следующей проверки всё ещё определяется моделью и guard
повторов; это не законченный планировщик параллельных направлений этапа 15.

Команда `questions TASK_ID` и пункт меню «ВОПРОСЫ» читают очередь без API/сети.
Ответ сохраняется через `--answer ID --decision approve|decline|information`
и необязательный `--note-file PATH`, либо вводится в меню. После ответа обычный
`resume` продолжает работу; завершённые шаги не повторяются. Консоль остаётся
в меню во время ожидания, фонового демона нет.

Ответ не устанавливает пакет, не расширяет scope и не повышает числовой бюджет.
Такие изменения выполняются оператором существующими средствами; сохранённые
границы затем проверяются заново. Для `flag_confirmation` явный approve вызывает
существующий `flag_verify.operator_confirm` для одного привязанного кандидата
в той же транзакции. Это операторское подтверждение, не новое сетевое наблюдение.
Модель и MCP-инструменты чтения не могут отвечать на вопросы. Автоматическая
проверка достаточного HTTP/Git-доказательства сохранена: обязательный ручной
вопрос для каждого технически подтверждённого флага этим этапом не введён.

## Старые состояния и исходы

`--approve-step` и `a:ID` удалены из CLI/меню. Backend явно отклоняет старый
параметр. ACCESS, ожидающий старого gate без признаков исполнения, становится
failed с `legacy_access_gate_retired_not_started`: это отменённое намерение,
не выполненная операция. Оригинальная запись и причина находятся в
`pm_operator_policy_events` и памяти. Сомнительное ожидание с отчётом, признаками
запуска или неизвестным исходом становится running/unknown и не перезапускается.
Старые significant/access-state паузы освобождаются при реальном продолжении;
read-only просмотр их игнорирует, не меняя доказательства.

Legacy Evidence Hub/ролевой цикл не получают ACCESS gate. В synthetic
`scheduler_harness` прежние privilege_escalation события не блокируют цикл и
не помечаются одобренными. Отдельные запреты изменений хоста не становятся
разрешениями. Смена режима не обходит настоящий неизвестный исход или активный
вопрос; legacy-цикл не выбирает независимые ресурсные ветки, для этого используется
coordinated-режим.

Кандидаты (`pm_assets`, credential) отделены от принятия данных сервером
(`pm_credential_acceptance`: цитата и исходный result_id проверенного отчёта),
а оно — от shell/execution в `pm_access_state`. Принятие данных не повышает
уровень доступа и не создаёт ручной паузы. Это интерпретация результата с
проверяемой цитатой, не универсальный детектор успешной авторизации по stdout.
Требуется свежий результат с сетевым происхождением; старый ID, readback/cached
и неизвестное происхождение не создают запись принятия. Неподтверждённое заявление
о принятии остаётся `credential_assessment` в памяти для планирования, не
`report_incomplete`. Противоречивое заявление о полученном shell рассматривается
отдельно и по-прежнему не публикует неподтверждённый доступ.

## Запрет смены паролей и пределы проверки

Один bounded guard в исходнике standalone `netguard_root.py` используется также
MCP и непривилегированной обёрткой. Запрещены распознаваемые passwd/chpasswd/
smbpasswd/kpasswd/chntpw, usermod/useradd с password-аргументом, известные формы
SSH/shell/SQL/PowerShell смены пароля и записи в passwd/shadow. Проверяются
generic argv, открытие/ввод сессии и текст PoC при запуске; брокер проверяет
локальный PoC, включая изменённый после копирования. Чтение `/etc/passwd`
сохраняется разрешённым.

Это не доказательство отсутствия смены пароля в произвольном коде, обфускации,
новом HTTP API или бинарнике. Проверка может быть консервативной. Условия комнаты
и запрет остаются в общих инструкциях. Установленную root-копию брокера при
разработке не меняли: для её нового guard потребуется обычное операторское
обновление root-owned файла. Новые MCP/обёртка уже отклоняют поддержанные формы
до привилегированной границы. sudo при разработке не использовался.
