# Требования и план переработки PM

Общий документ следующих этапов Lucky755/pm, исходная проверка кода —
`f0c30e7`, 14 ноября 2026. Это не заявление о завершении переработки.
Последующие задания уточняют требования, порядок реализации и критерии приёмки.
Каждый этап сверяется с фактическим checkout и сохраняет уже работающие проверки.

## Границы разработки

- Одна Kali, один оператор, ручной запуск. Фоновый демон, Orca, распределённое
  исполнение, запасные провайдеры и денежные бюджеты не входят в план.
- Рабочие задачи, SQLite, отчёты, журналы, capture и прочие доказательства
  при разработке не изменяются. Миграции проверяются на временных БД/копиях.
- Реальные CTF-цели и платный API требуют отдельного задания. Offline-проверки
  используют временные данные и заглушки внешних границ. SDK/MCP-smoke допускает
  только loopback fake API и временную конфигурацию, без sudo и целевых команд.
- Новый result_id, повторное чтение и новый отчёт сами по себе не являются
  новым знанием. Завершение роли и exit_code=0 не подтверждают цель исследования.

## Целевая архитектура — требования будущих этапов

1. **Предметная оркестрация принадлежит PM.** PM хранит цели, условия комнаты,
   разрешения, состояние исследования, направления и решения следующего шага.
   Harness используется для исполнения агентов: инструментов, сессий, событий,
   ограничения контекста и имеющихся средств runtime. Его возможности проверяются
   на установленной версии; PM не воспроизводит без необходимости общий agent loop.
2. **Все модельные обращения идут через общий адаптер Harness.** Планировщик,
   координатор, роли, анализ доказательств и исправление отчётов используют один
   проверяемый путь вызова, политику инструментов и диагностику. Реализован
   `orchestrator/model_adapter.py`: прямые HTTP-вызовы удалены, все производственные
   пути используют Harness. Проверки и ограничения описаны в
   [HARNESS_CAPABILITIES.md](HARNESS_CAPABILITIES.md).
3. **Работа внутри задания автоматическая.** Выбор ACCESS не должен требовать
   отдельного одобрения каждого шага. Разрешения задаются заданием и условиями
   комнаты; выбор модели не расширяет их. Миграция этой политики ещё впереди:
   текущий coordinated-код требует `--approve-step` для каждого ACCESS.
4. **Обычные находки не останавливают цикл.** Ссылки, версии, заголовки,
   отрицательные проверки и переходы между ролями обновляют память. Неизвестный
   исход, повреждённый/противоречивый отчёт и исчерпание бюджета требуют явного
   исхода и сохранения состояния, а не выдуманного успеха или слепого повтора.
5. **Вопросы оператору содержательны:** pivoting/расширение scope, получение
   инструментов или документации, расширение вычислительного/инструментального
   бюджета и подтверждение флагов. Точные переходы, включая соотношение решения
   оператора и локальной проверки происхождения флага, уточняются следующим
   заданием. Сейчас проверяемый capture может автоматически подтвердить флаг и
   цель; обязательное ручное подтверждение каждого флага ещё не введено.
6. **Общая обновляемая память** объединяет цели, сервисы, гипотезы, опровержения,
   наблюдения, доступ и доказательства с происхождением и областью применимости.
   Полезные сессии сохраняются и могут использоваться далее. Несколько направлений
   исследования могут существовать параллельно в пределах одной машины и общих
   разрешений; отмена одного направления не уничтожает остальные.
7. **Смена паролей запрещена, условия комнаты обязательны.** Условие задания
   сохраняется во всех промптах и проверках действий. Нужны проверяемые ограничения
   исполнения; одной инструкции модели недостаточно. Глобальный жёсткий запрет
   любых способов смены паролей ещё не доказан, включая произвольные SSH/PoC.

Частичная реализация памяти не означает сохранение полезных живых сессий:
`run_role()` сейчас закрывает task-сессии перед и после роли. Координатор
выполняет одну роль последовательно; сохранённых параллельных ветвей пока нет.
Доступ всё ещё требует отдельного одобрения. Эти ограничения не снимаются
текущими исправлениями отчётов.

## Следующие этапы — запланировано, не реализовано

1. Общий адаптер реализован и проверен offline/loopback в текущем изменении.
   Следующая переработка использует этот путь; внешний API не проверялся.
2. Исполнение в пределах задания без одобрения каждого ACCESS; вопросы только
   на определённых границах. Не расширять одну попытку до перебора.
3. Единая модель памяти и направлений, жизненный цикл полезных сессий,
   восстановление без повторения действий с неизвестным исходом. Для этапа 15
   выполнен только локальный прототип двух специалистов с событиями, MCP и
   независимой отменой через отдельные SDK runtime. Штатные subagents/workflow
   в используемом профиле недоступны; parallel PM ещё не реализован.
   См. [проверенные механизмы и ограничения](HARNESS_CAPABILITIES.md).
4. Проверяемый контроль условий комнаты и запрета смены паролей на границе
   исполнения; тесты обходов через shell, SSH и PoC, без живых целей.
5. Уточнение политики операторского подтверждения флагов и ресурсных запросов.
   Не менять expected_flags, scope и бюджеты ради успешного завершения.

Для каждого пункта нужны отдельные критерии и проверка текущей версии кода.
Следующий промпт может уточнить или изменить этот порядок; его требования
не считаются заранее выполненными.

## Воспроизводимые проверки

```bash
.venv/bin/python -m orchestrator.check_environment
.venv/bin/python tests/run_offline.py
.venv/bin/python tests/run_offline.py --runtime
.venv/bin/python tests/run_offline.py --only test_report_semantics test_report_integrity test_coordinated_attack
```

[run_offline.py](../tests/run_offline.py) ведёт явный инвентарь всех `test_*.py`.
Каждый набор исполняется в отдельном Python-процессе: старые подмены
`sys.modules` не загрязняют соседние проверки. Шесть legacy-скриптов с assert
исполняются как скрипты, а не как «0 tests, OK». Сбой, timeout или пропуск
выбранной проверки не даёт зелёного результата. Проверка инвентаря находится в
[test_offline_runner.py](../tests/test_offline_runner.py).

`--runtime` использует установленный SDK, настоящий MCP stdio и loopback fake
API, временные БД и конфигурацию. Внешние запросы, GLM и привилегированное
исполнение заменены/запрещены; это не проверка настоящей CTF-машины.

Эксперименты с ключом/рабочим MCP/инфраструктурой перечислены в категории
MANUAL и никогда не импортируются offline-runner. Их непрохождение не
скрывается: runner явно печатает NOT RUN. Полный `unittest discover` по
старой папке не является безопасной командой: некоторые ручные скрипты имеют
действия при импорте. Изоляция старых тестов сейчас процессная; полный перевод
их всех в чистые unittest-модули ещё не выполнен.

Ограничения текущих проверок: анализ произвольной прозы не является NLU-доказательством;
неоднозначность остаётся неподтверждённой. Отказ сервера выводится из явного
структурированного исхода или ограниченных протокольных признаков отдельной
операции; произвольный stdout не заменяет доказательство доступа или флага.

Результат предыдущего изменения (14.11.2026): 427 offline unittest-проверок,
шесть legacy assert-скриптов и отдельно три SDK/MCP smoke-проверки прошли.
Пропусков в выбранных наборах нет. В sandbox loopback-сокет запрещён, поэтому
SDK/MCP-набор был повторён с разрешённым локальным сокетом; это не обращение к
реальным целям или провайдеру модели. Оба self-test (`agent_actions`, `flag_verify`)
завершились успешно. Ручные API/инфраструктурные эксперименты не запускались.

Проверка общего адаптера (14.11.2026, база `fbeef2d`): 440 offline unittest,
шесть legacy assert-скриптов, девять настоящих SDK/MCP loopback-проверок.
Пропусков в выбранных наборах нет; оба self-test и environment check проходят.
Ручные проверки API/инфраструктуры не запускались. Runtime-тесты используют
локальные сокеты с разрешением sandbox; рабочие задачи и доказательства не
изменяются. Автоматический ACCESS, долговременные сессии, расширенная память
и политика вопросов оператору остаются запланированными.
