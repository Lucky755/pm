# Требования и план переработки PM

Общий документ следующих этапов Lucky755/pm, исходная проверка кода —
`f0c30e7`, 14 ноября 2026. Это не заявление о завершении переработки.
Последующие задания уточняют требования, порядок реализации и критерии приёмки.
Каждый этап сверяется с фактическим checkout и сохраняет уже работающие проверки.

## Границы разработки

- Одна Kali, один оператор, ручной запуск. Фоновый демон, Orca, распределённое
  исполнение, запасные провайдеры и денежные бюджеты не входят в план.
- Рабочие задачи, SQLite, отчёты, журналы, capture и прочие доказательства
  при разработке не изменяются. Миграции проверяются на временных БД/копиях.
- Реальные CTF-цели и платный API требуют отдельного задания. Offline-проверки
  используют временные данные и заглушки внешних границ. SDK/MCP-smoke допускает
  только loopback fake API и временную конфигурацию, без sudo и целевых команд.
- Новый result_id, повторное чтение и новый отчёт сами по себе не являются
  новым знанием. Завершение роли и exit_code=0 не подтверждают цель исследования.

## Целевая архитектура — требования будущих этапов

1. **Предметная оркестрация принадлежит PM.** PM хранит цели, условия комнаты,
   разрешения, состояние исследования, направления и решения следующего шага.
   Harness используется для исполнения агентов: инструментов, сессий, событий,
   ограничения контекста и имеющихся средств runtime. Его возможности проверяются
   на установленной версии; PM не воспроизводит без необходимости общий agent loop.
2. **Все модельные обращения идут через общий адаптер Harness.** Планировщик,
   координатор, роли, анализ доказательств и исправление отчётов используют один
   проверяемый путь вызова, политику инструментов и диагностику. Реализован
   `orchestrator/model_adapter.py`: прямые HTTP-вызовы удалены, все производственные
   пути используют Harness. Проверки и ограничения описаны в
   [HARNESS_CAPABILITIES.md](HARNESS_CAPABILITIES.md).
3. **Работа внутри задания автоматическая.** Выбор ACCESS не должен требовать
   отдельного одобрения каждого шага. Разрешения задаются заданием и условиями
   комнаты; выбор модели не расширяет их. Реализовано от `9cfce64`: ACCESS без
   отдельного одобрения; прежние gates не блокируют цикл. Проверки конкретной
   операции, scope, триажа и неизвестного исхода сохранены.
4. **Обычные находки не останавливают цикл.** Ссылки, версии, заголовки,
   отрицательные проверки и переходы между ролями обновляют память. Неизвестный
   исход, повреждённый/противоречивый отчёт и исчерпание бюджета требуют явного
   исхода и сохранения состояния, а не выдуманного успеха или слепого повтора.
5. **Вопросы оператору содержательны:** pivoting/расширение scope, получение
   инструментов или документации, расширение вычислительного/инструментального
   бюджета и подтверждение флагов. Реализована сохраняемая ресурсная очередь
   вопросов, CLI/меню и ответы. Оператор может подтвердить конкретный кандидат
   через прежний путь. Достаточный capture по-прежнему может автоматически
   подтвердить флаг и цель; обязательный ручной вопрос для каждого не введён.
6. **Общая обновляемая память** объединяет цели, сервисы, гипотезы, опровержения,
   наблюдения, доступ и доказательства с происхождением и областью применимости.
   Полезные сессии сохраняются и могут использоваться далее. Несколько направлений
   исследования могут существовать параллельно в пределах одной машины и общих
   разрешений; отмена одного направления не уничтожает остальные.
7. **Смена паролей запрещена, условия комнаты обязательны.** Условие задания
   сохраняется во всех промптах и проверках действий. Нужны проверяемые ограничения
   исполнения; одной инструкции модели недостаточно. Реализован bounded guard
   распознаваемых операций в MCP/обёртке/исходнике standalone broker. Это не
   гарантия анализа произвольного кода; установленный root-owned файл не обновлялся.

## Воспроизводимые проверки

```bash
.venv/bin/python -m orchestrator.check_environment
.venv/bin/python tests/run_offline.py
.venv/bin/python tests/run_offline.py --runtime
.venv/bin/python tests/run_offline.py --only test_report_semantics test_report_integrity test_coordinated_attack
```

[run_offline.py](../tests/run_offline.py) ведёт явный инвентарь всех `test_*.py`.
Каждый набор исполняется в отдельном Python-процессе: старые подмены
`sys.modules` не загрязняют соседние проверки. Шесть legacy-скриптов с assert
исполняются как скрипты, а не как «0 tests, OK». Сбой, timeout или пропуск
выбранной проверки не даёт зелёного результата. Проверка инвентаря находится в
[test_offline_runner.py](../tests/test_offline_runner.py).

`--runtime` использует установленный SDK, настоящий MCP stdio и loopback fake
API, временные БД и конфигурацию. Внешние запросы, GLM и привилегированное
исполнение заменены/запрещены; это не проверка настоящей CTF-машины.

Эксперименты с ключом/рабочим MCP/инфраструктурой перечислены в категории
MANUAL и никогда не импортируются offline-runner. Их непрохождение не
скрывается: runner явно печатает NOT RUN. Полный `unittest discover` по
старой папке не является безопасной командой: некоторые ручные скрипты имеют
действия при импорте. Изоляция старых тестов сейчас процессная; полный перевод
их всех в чистые unittest-модули ещё не выполнен.

Ограничения текущих проверок: анализ произвольной прозы не является NLU-доказательством;
неоднозначность остаётся неподтверждённой. Отказ сервера выводится из явного
структурированного исхода или ограниченных протокольных признаков отдельной
операции; произвольный stdout не заменяет доказательство доступа или флага.

Результат предыдущего изменения (14.11.2026): 427 offline unittest-проверок,
шесть legacy assert-скриптов и отдельно три SDK/MCP smoke-проверки прошли.
Пропусков в выбранных наборах нет. В sandbox loopback-сокет запрещён, поэтому
SDK/MCP-набор был повторён с разрешённым локальным сокетом; это не обращение к
реальным целям или провайдеру модели. Оба self-test (`agent_actions`, `flag_verify`)
завершились успешно. Ручные API/инфраструктурные эксперименты не запускались.

Проверка общего адаптера (14.11.2026, база `fbeef2d`): 440 offline unittest,
шесть legacy assert-скриптов, девять настоящих SDK/MCP loopback-проверок.
Пропусков в выбранных наборах нет; оба self-test и environment check проходят.
Ручные проверки API/инфраструктуры не запускались. Runtime-тесты используют
локальные сокеты с разрешением sandbox; рабочие задачи и доказательства не
изменяются. Автоматический ACCESS, долговременные сессии, расширенная память
и политика вопросов оператору остаются запланированными.

## Этап инструкций — реализовано, проверка от базы `66b25b8`

Общий источник поведения — `instructions/PM.md`; назначения RECON, VULN,
ACCESS, VERIFY отделены от специализации и разрешений. Реализованы явные
`http-surface`, `capture-audit`, `access-triage` с контрактом входов/результата,
процедурой, списком инструментов и потолком бюджета. Старые вызовы наследуют
профиль роли. Код проверяет совместимость роли/профиля; новые разрешения не
выдаются. Набор инструментов ограничивается в Harness до MCP dispatch.

Убраны расходящиеся полные/сжатые How-to-work и CTF-эвристики про конкретную
структуру бинарника, тайминги рассуждения и безусловные параметры полного скана.
Советы по бинарному анализу оставлены отдельной неподключаемой справкой без
заявления о проверенности. HTTP/capture/triage-процедуры перечисляют реальные
offline-проверки; текст процедуры загружается только выбранным профилем.

Координатор, первоначальное планирование, специалисты, форматирование и
вспомогательные/legacy-анализы используют общий блок и явный режим исполнения.
Схемы отчётов, scope, NetGuard, evidence validators, triage gate и действующие
операторские checkpoints остались в коде. Установка SDK не менялась.
Автоматический ACCESS без каждого одобрения, полезные долговременные сессии,
единая расширенная память, новый контроль условий комнаты и параллельные
направления остаются запланированными; параллельное исполнение — этап 15.

Проверено: 449 offline unittest, шесть legacy assert-скриптов и десять настоящих
SDK/MCP loopback-проверок (семь в adapter runtime, одна coordinated, две readonly),
без пропусков. Две новые проверки сначала воспроизвели отсутствие общего блока
и загрязнение промпта нерелевантными советами. Оба self-test, environment check,
compileall и git diff --check проходят. Платный API, рабочая инфраструктура и
реальные CTF-цели не вызывались. Runtime-тесты запускались с разрешённым локальным
сокетом; рабочие задачи/БД/отчёты/доказательства не изменялись.


## Этап памяти — реализовано от `9b275d9`

В существующей SQLite добавлена версионируемая память. Текущее структурированное
состояние, история операций/изменений и полные исходные материалы разделены.
CAS/savepoints проверяют версию и атомарность, коррекция сохраняет причину и
историю. Миграция добавочная; рабочие данные при разработке не менялись.

Координатор/специалисты используют полный индекс ресурсов/материалов и все
существенные сохранённые факты; первые 12 сервисов и последние N отчётов больше
не определяют доступность знания. Совместимые краткие окна оставлены для показа.
Контекст выбирает релевантные byte ranges, хранит SHA/охват/пропуски и не считает
readback, delivered range или agent-reported analysis новым наблюдением.
Вспомогательные анализы получают metadata-only представление той же памяти.

Перед executor ведётся canonical resource/operation/parameters guard, включая
импорт прежних выполненных вызовов. Новая формулировка/ID не разрешают повтор.
Неизвестный исход требует явного рассмотрения; точная связь с сохранённым
result_id позволяет восстановить известное завершение без второго запуска.

Стабильные инструкции отделены от изменяемого состояния. Размеры запроса и
префикса измеряются; SDK-reported input/output/cache-read учитываются с null
для отсутствующих показателей. Новых API-параметров кэширования нет; fake usage
не объявляется доказательством production cache или сокращения общего счёта.
Сценарий: оригинал 300018 байт, выбранные данные 4096, memory JSON 7153,
PM-промпт 23573, стабильный префикс 8664 байта. Это измерение объёма, не оплаты.

Границы, схема, API и ограничения описаны в [TASK_MEMORY.md](TASK_MEMORY.md).
Живые сессии/параллельные направления, универсальная семантика произвольного
shell и новый UI разрешения повтора неизвестного исхода не реализованы.
Одобрения ACCESS, scope/NetGuard, реальные цели и доказательства не ослаблялись.

Проверено: 478 offline unittest и шесть legacy assert-скриптов; отдельно
11 настоящих SDK/MCP loopback-проверок (восемь adapter, одна coordinated, две
readonly). Пропусков в выбранных наборах нет. Новые 29 проверок памяти включают

## Исправления повторов этапа 4 — от `0fde4f8`

проверяемым подмножеством TCP-проверки `/usr/bin/nmap` с явными портами и одним

[TASK_MEMORY.md](TASK_MEMORY.md#учёт-повторов). Это не изменение scope/бюджетов

## Автономность и очередь вопросов — реализовано от `9cfce64`

Удалены обязательное одобрение ACCESS и significant_finding как управляющая
остановка. Специальный классификатор явно отключён как gate; ни его pending
записи, ни прежний run status не блокируют обычную работу. Проверены реальные
пути new/resume/attack, legacy cycle и synthetic Harness scheduler. Старые
ожидания без исполнения отменяются как not_started с оригиналом в истории;
неизвестный исход сохраняется и не воспроизводится автоматически.

Реализована SQLite-очередь pivoting/tool/budget/flag_confirmation. Сохраняются
ID, причина, границы, ресурсная ветка, ссылки, ответ и события. Независимая
ветка может продолжить работу, просмотр ожидания не обращается к модели/сети,
консоль остаётся доступной. Ответ не расширяет scope и бюджеты. Явное
подтверждение выбранного флага использует существующий операторский путь
атомарно с ответом; новые доказательства при этом не выдумываются.

Кандидат учётных данных, подкреплённое цитатой принятие данных сервером и
фактический shell/execution разделены для планирования. Нестандартный ответ
проходит модельную интерпретацию и память, не требует фиксированной категории.
Повреждённый/противоречивый отчёт, невалидное управляющее решение, scope и
неизвестный исход исполнения по-прежнему имеют явную проверку.

Запрет смены паролей внесён в общие инструкции и поддержанные границы операций:
MCP, непривилегированная обёртка, исходник standalone broker. Произвольный
shell/обфускация/новые API не объявляются полностью проверенными. Установленный
root-owned broker не изменяли и sudo не использовали. Детали и ограничения —
[OPERATOR_QUESTIONS.md](OPERATOR_QUESTIONS.md).

Новые проверки сначала воспроизвели шесть отсутствовавших свойств автономности;
затем сценарии расширены до 17 тестов: цепочка ACCESS, Git/секрет без паузы,
неизвестный протокол через настоящий run_role, очередь/ответ/rollback/перезапуск,
независимый сервис, CLI без API, legacy gate и поддержанные password-операции.
Тесты прежних обязательных одобрений актуализированы под новые требования;
проверки повреждения отчёта, резервирования номера и неизвестного исхода сохранены.

Итоговый `.venv/bin/python tests/run_offline.py --runtime`: 516 unittest
(505 offline + 11 настоящих SDK/MCP loopback), шесть legacy assert-скриптов,
ноль сбоев и пропусков. Оба self-test (`agent_actions`, `flag_verify`), compileall
и `git diff --check` проходят. Ручные API/инфраструктурные эксперименты не
запускались. Настоящие SDK/MCP работали с loopback fake API и временными данными;
реальная цель, GLM, sudo и рабочая SQLite не использовались.

Ограничения: ветки очереди привязаны к известным сервисам или всей задаче;
это последовательное продолжение независимой работы, а не параллельный workflow.
Ответы pivoting/tool/budget не выполняют привилегированную настройку и не меняют
границы молча. Новая политика не снимает остановок на неизвестном исходе и
повреждённом/противоречивом отчёте. Неподтверждённое принятие учётных данных
сохраняется как неопределённость для модели, без повышения доступа и ручной паузы.
