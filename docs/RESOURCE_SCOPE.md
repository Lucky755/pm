# Область исследования и ресурсы

Реализовано от `899716c`. [resources.py](../orchestrator/resources.py) хранит
модель задачи; чистый контракт проверки используется PM и исходником
[NetGuard](../executor/netguard_root.py). Рабочие задачи при разработке не менялись.

## Ввод и область

`new --target` принимает IPv4, IPv6, домен, HTTP/HTTPS URL. Исходная строка,
домен, схема, порт, путь, query и fragment сохраняются отдельно. `tasks.target`
остаётся конкретным адресом для совместимости исполнителя; это не замена
исходного URL. Unicode-домен нормализуется в IDNA, Unicode URI — в percent-encoding
для запроса, полный исходный ввод остаётся в памяти. IPv6 URL использует скобки.
Встроенные URL-логин/пароль, неоднозначный ввод, loopback Kali и адреса документации
не принимаются как прямая живая цель. Loopback назначения SSRF рассматривается
отдельно в контексте целевого приложения.

| Область (`--area`) | Разрешение |
|---|---|
| `web` — веб-ресурс | Названный сайт/origin, закреплённые адреса и HTTP-пути. Нет обязательного полного скана IP, generic exec, PoC или shell |
| `host` — хост | Сервисы конкретной машины. Домен или URL с доменом требует явного `--address`: DNS не доказывает принадлежность всей машины. Буквальный IP в URL уже задаёт адрес |
| `lab` — среда лаборатории | Явные машины и `--allow-network CIDR`. Связь, маршрут и способ обращения проверяются отдельно |

Для IP по умолчанию выбирается host, для домена/URL — web. Ввод домена
без указанной схемы разрешает HTTP:80 и HTTPS:443 этого домена; явный URL
сохраняет именно его origin/порт. Это не разрешение других портов общего IP.
Веб-точка входа в new/resume использует coordinated-маршрут; явный `--legacy` несовместим. Старые задачи без
метаданных сохраняют прежний маршрут до явной смены адреса/нового задания.
Область доступна при создании в меню; для лаборатории запрашиваются CIDR.
Веб-меню не предлагает неиспользуемый legacy-режим. Для host с доменом меню
запрашивает явные адреса вместо выдачи машинных прав из DNS.
Сохранённая область не меняется от выбора роли или следующего ответа модели.

Дополнительные параметры создания:

- `--address IP` (повторяется) — явное закрепление вместо DNS;
- `--hostnames a.lab,b.lab` — явно заданные виртуальные хосты на адресах машины;
- `--allow-resource URL` — дополнительный origin исследования; IP допустим
  только в lab. URL не даёт права сканировать весь обслуживающий его IP;
- `--page-resource URL` — разрешённая зависимость страницы: один точный URL,
  включая query, без обхода каталогов/исследования её узла;
- `--deny-resource DOMAIN|URL|CIDR` — явное исключение комнаты; имеет приоритет;
- `--path-prefix /app/` — граница HTTP-путей, без query. `/app2` не входит в `/app`;
- `--ssrf-destination URL` — точное назначение через исходное приложение,
  включая target-relative 127.0.0.1/::1.

Буквальный IP в URL нельзя переопределить другим `--address`. Это не виртуальный
хост; HTTP-запрос к loopback цели оформляется через SSRF, а не подменой адреса.

Обнаруженная ссылка, redirect и DNS-ответ — сведения, не разрешения. Поддерживающая
загрузка страницы и активное исследование CDN/стороннего сервиса различаются
в связях и политике. Непредусмотренная сторонняя загрузка не выполняется сама.
Условия комнаты сохраняются в intent; технические исключения/границы задаются
явно. Универсального перевода произвольных естественных ограничений в firewall нет.

## Маршрут исполнения

Веб-запуск: сохранение исходного HTTP capture → общая память/карта → координатор.
Программно не запускаются tcp_full, preflight общего IP, четыре Evidence Hub
анализа или отдельный DECIDE. Начальные HTTP-операции используют `--max-jobs`
и прежний общий HTTP-бюджет. `--reprobe`, `--sync-burp`, явный `--max-rounds`
для этого маршрута отклоняются; параметры не игнорируются.

Для host сохраняются прежние начальная разведка и кэш. Для lab с приложением
в роли входа без разрешения исследовать его IP начальная проверка также HTTP.
Координатор получает граф и разрешённые ресурсы. В ссылках могут присутствовать
наблюдаемые внешние данные, но run_role не принимает их как активную границу.
Pivoting-вопрос может ссылаться на такой ресурс и сохраняет зависимую ветку.
Ответ на него сам не меняет разрешённые сети или root-конфигурацию.

`pm_http_capture` закрепляет фактический адрес и Host/SNI, сохраняет query и
исходные байты. Fragment остаётся браузерными данными, не частью HTTP-запроса.
URL globbing curl отключён; один URL не разворачивается в несколько запросов.
Редиректы, cookies, произвольные заголовки и тела запроса автоматически не
добавляются; проверка TLS сохранена. HTTP GET не доказывает отсутствия
побочных эффектов сервера. Для origin-only разрешений/URL-исключений произвольный
shell/PoC не выдаётся за проверяемое исполнение в таких границах и отклоняется.
IP-исключения также стоят перед разрешающими правилами firewall.

## SSRF

`pm_http_ssrf(task_id, application, destination, parameter='url', context='')`
зарегистрирован в MCP и доступен профилю http-surface. Поддерживается один
bounded GET/query-parameter сценарий. PM и root-брокер проверяют origin исходного
приложения, его закреплённый адрес, URL назначения и контекст целевой машины.
Назначение разрешено точным SSRF-grant либо явной сетью lab; исключения комнаты
проверяются первыми. Чужое приложение, произвольное назначение, иной контекст,
неоднозначный повтор параметра и выход из path boundary отклоняются.

Кали подключается только к приложению. Remote loopback не разрешается как
loopback Kali и не получает прямого сетевого маршрута. Capture хранит способ
обращения, исходный запрос и назначение. Это доказательство ответа приложения;
факт контакта внутреннего назначения остаётся непроверенным без содержательного
подтверждения. Повтор возвращает тот же артефакт, не новое наблюдение.
Другие SSRF-транспорты/методы и универсальный анализ произвольного PoC не реализованы.

## Хранение и смена IP

В существующей SQLite добавлены `pm_resource_scope` (версия, вход, политика,
состояние смены адреса), `pm_resources`, `pm_resource_links`, `pm_resource_events`.
Ресурсы: logical machine, address, domain, origin, service, path и способ
достижения. Связи сохраняют источник и время; вопрос pivoting связан с ресурсом.
Разные дополнительные endpoint не объявляются одной физической машиной по DNS.

Граф читает структурированные сервисы через общий service_inventory с проверкой
task/адреса/scope, не создаёт другую БД доказательств. Наблюдения сохраняют
исходные ссылки SQLite/result_id/artifact_ref; configured endpoint не называется
открытым портом или установленным продуктом. Полный и сжатый промпты получают
граф через память. Чтение контекста не изменяет БД и не вызывает DNS/сеть.

HTTP-наблюдения имеют ключ task + address + origin + request path. Разные
закреплённые адреса не перезаписывают один другой. Идемпотентная миграция старой
уникальности сохраняет ID, все колонки, индексы, триггеры и связанные записи
refresh. Если появится неучтённый FK-consumer, миграция явно откажет, а не удалит
его данные. Сам capture-store и формат capability log не меняются.

`change-ip TASK_ID --target IP` означает ту же логическую машину. Task ID,
файлы, intent, цели, отчёты, candidate credentials, доступы и история остаются.
Прежние отчёты/артефакты сохраняют исходный адрес. Pending-вопросы флагов остаются
доступны. Старый доступ — сведения с неизвестной текущей живостью, а не новая
авторизация. Planned-поручение с устаревшими границами сохраняется как отменённое
до запуска; его исход не называется ошибкой SSH. Running/unknown блокирует
смену до явного разбора.

Сначала проверяется маршрут и поддержка брокера, затем заменяется изоляция
и сохраняется переход. Проверяются известные соединения (для web — исходный
HTTP endpoint). Отдельного нового плана модели и полного скана нет. Успешная
проверка сохраняется, обычное следующее resume не повторяет её. Прерванная
смена остаётся connections_pending; история перехода и старые файлы сохранены.
Незавершённые legacy successor-переходы поддерживаются прежним протоколом.
`--archive-work` остаётся параметром старого successor-протокола; для новой
смены IP он явно отклоняется, поскольку файлы остаются на месте. У миграционного
маршрута `--reprobe`/`--sync-burp` не игнорируются: неподдерживаемая комбинация
отклоняется до изменения изоляции. Новые необходимые проверки поручаются роли.

## Проверки и ограничения

[test_resource_scope.py](../tests/test_resource_scope.py) проходит реальные PM
new/resume/change-ip, сборку контекста, публичную регистрацию MCP, проверки
границ и настоящее временное хранилище артефактов. Заменены модель/первоначальный
план и граница привилегированного executor. Проверяются IPv6/IDNA/query/fragment,
несколько адресов/виртуальных хостов, зависимости страницы, SSRF, pivoting,
миграция HTTP, сохранение истории и неизвестного исхода, отсутствие повторного скана.

Установленный root-owned брокер при разработке не обновлялся. Новым задачам
нужна версия исходника с `resource_policy_protocol=1`; PM явно отказывает
старому брокеру, сохраняя созданную задачу, intent и цели. Нужна обычная
операторская установка брокера перед живым запуском. SDK/зависимости не менялись.
Kernel namespace/NAT6, реальный VPN/DNS, IPv6 firewall Docker и настоящие цели
без sudo/сети не проверялись: offline покрывает правила/аргументы/политику.
Callback listener пока IPv4. Сложные браузерные загрузки, произвольные SSRF,
универсальная семантика shell и UI редактирования root-грантов по ответу на
вопрос остаются следующими этапами. Сохранённый ответ не расширяет права молча.
