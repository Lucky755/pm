# Сессии, SSH-forward и входящие соединения задачи

Реализовано от `c8f0e78`. PM хранит связь ресурса, пользователя, назначения,
полезности, состояния, владельца и зависимостей в `pm_task_sessions`,
`pm_session_dependencies`, историю — в `pm_session_events`. Память задачи и
контекст координатора используют этот источник; исходные capability logs и
ролевые отчёты сохраняются. Новый ID сессии/владельца не подтверждает новый факт.
Сессии Harness перечисляются отдельно: закрытый runtime не считается сохранённым
SSH/PTY-подключением.

## Владение и жизненный цикл

`pm_session` сохраняет прежние open/send/read/interrupt/close/list и добавляет
resource, username, purpose, retain и ssh_json. По умолчанию полезная сессия
сохраняется. Агент закрывает ненужную либо выставляет retain=false; в конце роли
менеджер закрывает её, если нет действующего маршрута-зависимости. Полезность —
явное назначение агента/оператора, не выдуманная классификация по stdout.
Окончание run_role освобождает владение, **не закрывает все сессии задачи**.
Обычная явная teardown/cleanup по-прежнему завершает процессы задачи.

Лимит broker — десять живых сессий, включая входящие callback. Проверка квоты и
открытие сериализованы между процессами. Idle timeout по-прежнему 60–7200 секунд,
по умолчанию 1800; это не обещание вечного подключения и не новый фоновый daemon.

Каждая роль имеет уникальный PM_SESSION_OWNER; он явно передаётся SDK/MCP.
Broker хранит владельца и PID/start-time, сериализует операции и отклоняет другого
живого владельца **до ввода или потребления буфера**. Старый PID не достаточен:
проверяется поколение процесса. После смерти агента владение можно получить
заново. Потерянная публикация worker PID восстанавливается через уже
существующий control socket; повреждённая metadata сохраняется как unknown
занятый slot. После передачи/восстановления сначала прочитайте терминал. Незавершённый
broker-запрос ввода оставляет pending_unknown: повтор запрещён, допустимы чтение,
interrupt/закрытие или проверка оператором. Отмена команды и её неизвестный исход
не превращаются в выполненную проверку. Owner/описание не входят в подпись
исследовательской операции и не обходят guard повторов. Сравнивается состояние
после предыдущего ввода: одинаковый ответ не разрешает повтор. Paging того же
буфера не меняет его hash; новое поступившее I/O может изменить условия
интерактивного управления, но не становится автоматически новым фактом цели.

Начальный bash без startup-файлов — создание локального терминала, не сетевой
зонд. Произвольный argv и managed SSH не получают такого исключения. Локальное
чтение буфера/list/readback не создаёт независимое сетевое доказательство.

SQLite сама по себе не доказывает живость. При следующей роли менеджер проверяет
worker PID/start-time и настоящий Unix control protocol; пропавшие подключения
помечаются disconnected, недоступная проверка — unknown. Для managed SSH проверка
может выполнить фиксированный POSIX `true` через **существующий** ControlMaster:
BatchMode и ProxyCommand=false исключают новую авторизацию при потере master.
Это bounded maintenance, без модельного запроса. Non-POSIX shell/ограниченный
аккаунт может не пройти этот профиль: сохраняется unverified, не выдумывается
ошибка пароля. Обычный list не исполняет удалённую команду. Профили локального аудита без
pm_session не получают remote health даже при наличии сохранённого SSH. Имена пользователей
помечены как заявленные/настроенный login; реальные доступы проверяются отдельно.
TCP half-open и ещё не обнаруженный разрыв нельзя доказать строкой в БД:
remote_liveness остаётся неизвестной без текущего I/O/проверки. Контекст другого
ручного run помечает старую живость unknown, пока исполнитель её не обновит.

## Разрешённый pivot

Managed SSH открывается через `pm_session(..., ssh_json=...)`:

```json
{"target":"10.0.0.1","user":"student","port":22,"identity":"/work/keys/id_ed25519"}
```

identity может быть пустой. Host/address/permissions проверяются существующими
scope/NetGuard; generic argv и ssh_json несовместимы. Персональный known_hosts
лежит в workspace. Control socket расположен в root-private каталоге и через
fd bind доступен только поддержанному SSH sandbox, не обычному PoC. Отключены
SSH local command/agent forwarding/escape commandline; произвольный root не выдан.

`pm_pivot_request` или typed `wait_operator` с kind=pivoting получает spec:

```json
{"source_session":"0123abcd","resource_ref":"resource:...",
 "destination":"10.2.0.5","port":8080,"local_port":18888,
 "probe":"http_headers","purpose":"Исследовать сохранённый внутренний сервис"}
```

Нужны сохранённые allow_pivot и allow_port_forward, уже разрешённый внутренний address и работающий
managed SSH master. Вопрос показывает исходную сессию, точное назначение/порт,
локальный endpoint, действия, права и цель. approve сначала сохраняет ответ,
потом авторизует root-owned квитанцию и создаёт **один** SSH local TCP forward.
decline сохраняет причину для другого направления и ничего не запускает.
Повтор запроса с теми же условиями возвращает прежний вопрос. Generic старый
pivoting-вопрос остаётся информационным и не создаёт маршрут автоматически.

Источник и назначение остаются внутри сохранённых условий комнаты. Это не
неявное разрешение новой сети/инфраструктуры. Изменение scope выполняется явно
оператором существующими средствами; этот профиль не обходит запрет pivoting.
Поддержан SSH TCP-forward, не полный IP-router, SOCKS/UDP/туннель любого PoC или
неоднозначный target-loopback. Произвольный legacy SSH без managed master не
переоборудуется тайно и не авторизуется повторно при восстановлении.

Endpoint 127.0.0.1:local_port находится **в namespace задачи**, а не на целевой
машине и не в обычной сети Kali. Первичная bounded HTTP HEAD либо banner-проверка
требует байтов от назначения. Локальное TCP connect к слушателю SSH само по себе
не подтверждает доступность внутреннего сервиса. Состояния active и
established_unverified разделены; сохранённая probe имеет время и происхождение.
`pm_pivot(..., action=probe)` явно проверяет сохранённый маршрут ещё раз;
status не является новым наблюдением цели.

Квитанция creating пишется **до** SSH-forward. После потери ответа, перезапуска,
unknown/broken source автоматического второго forward нет. apply/status читают
прежнюю квитанцию. `questions TASK_ID --apply-pivot ROUTE_ID` применяет ранее
одобренное намерение, если оно ещё approved/prepared, а не пересоздаёт unknown.
При обрыве источника зависимости помечаются broken_source, при недостоверной
проверке — source_unknown. Новый исходный канал означает новые условия и вопрос.
Модель/MCP не могут авторизовать квитанцию. Полный анализ произвольного shell
не является гарантией обнаружения всех обходов: техническая авторизация
относится к поддержанному профилю, условия задачи остаются обязательными.

Закрытие не заменяет идентичность маршрута ответом broker. Сохранённые
request_id/manifest проверяются (task, исходная сессия, ресурс и hash manifest),
ответ должен соответствовать им обоим. Timeout, короткий/неверный ответ или
ненулевой код broker оставляют маршрут и зависимость в unknown; исходная SSH
сессия удерживается даже при retain=false. Старый route_state/exit_code от probe
не подтверждает close. Только согласованный closed с exit_code=0 завершает
зависимость; последующая очистка источника не отменяет это закрытие.

Следующий status читает прежний request_id, не создаёт forward и не повторяет
close. Он может согласовать сохранённое закрытие broker после потери ответа.
Все изменения маршрута, зависимости и версии памяти сохраняются одной SQLite
транзакцией; при сбое памяти они откатываются вместе. Исход внешней операции
при этом не откатывается: повторно выясняется через status, без повторения команды.

У старой повреждённой записи нет автоматического восстановления по догадке:
MCP/очередь показывают pivot_receipt_incomplete, исходный receipt_json остаётся
нетронутым, новые команды по нему не отправляются. Даже ошибочно закрытая старая
dependency не разрешает менеджеру выбросить источник непроверенного маршрута.
Нужен разбор оригинальной root-owned квитанции оператором; этот этап не добавляет
автоматический импорт утраченных идентификаторов. Просмотр очереди остаётся
локальным, без sudo/сети/API.

## Callback: адрес и диагностика

`pm_callback(open)` получает IP/interface из текущего `ip -j route get` к
лаборатории и сверяет IP с адресами интерфейса. Автоматически подходят tun/tap/wg/
ppp/vpn; ens33/VMware/NAT и прежний VPN не угадываются. Слушатель привязан к
конкретному адресу. Для иной топологии оператор явно задаёт:

```bash
python3 pm.py callback-config 11 --address 10.8.0.42 --interface tun0 --reason "Текущий маршрут лаборатории"
```

Необязательный --advertise задаёт адрес для цели при явном NAT/port-forward.
Он не объявляется проверенным извне. Конфигурация/история сохраняются в broker;
scope не меняется. --attempt-limit 1..10 явно меняет предел вариантов трассы,
по умолчанию три. Модель не может сама выполнять callback-config. При том же
живом слушателе open идемпотентен; изменение mode/адреса/ожидаемого файла требует
явного закрытия. После исчерпания вариантов требуется диагностика/оператор,
а не новый порт в бесконечном цикле.

`pm_callback(diagnose)` различает неверный/устаревший IP, отсутствие/неготовность
приёмника и уже полученный callback. При наличии свежего scoped preflight PM
показывает проверенные недоступные порты либо неполный охват. Он не объявляет
всю сеть недоступной по нескольким портам. Если слушатель работает и callback
нет, исходящие ограничения цели — **возможная**, не установленная причина.
Неверный NAT mapping также не определяется однозначно по тишине. Просмотр
диагностики не запускает новый целевой preflight. Входящие peers ограничены
сохранённым scope; принятый интерактивный socket становится pm_session с
двусторонним I/O, не одноразовым 4 MiB дампом. Входящий канал использует
уже принятый peer-bound socket на Kali/VPN, не произвольный host executor.
После изменения scope новые команды старому peer блокируются; историю можно
прочитать и подключение закрыть.

## Файлы

`pm_transfer(open/read/close/diagnose)` использует отдельный приёмник и
`/work/transfers`. Это raw TCP stream + EOF; для nc нужен вариант, отправляющий
EOF, например -N. До начала задаются expected_bytes (либо -1 неизвестно),
необязательный SHA256 и byte budget. По умолчанию 512 MiB, максимум 1 GiB на файл,
резерв свободного места 64 MiB. Данные идут chunks ≤64 KiB прямо на диск, в private staging внутри task
workspace; агент не может изменить .part во время измерения хэша. Затем файл
публикуется атомарно и передаётся владельцу задачи.

Возвращаются измеренные bytes/SHA256, EOF, полнота и причина. Известный размер
и EOF подтверждают размер, хэш — соответствие ожидаемым bytes. Эти ожидания
объявлены вызывающим, не заменяют проверку происхождения/цели. Неизвестный размер
остаётся eof_unverified_size; timeout, лимит, нехватка места и несовпадение
размера/хэша оставляют .part и явный incomplete. Завершённый файл получает .bin
атомарно. Нет выдачи всего файла в stdout или универсального 4 MiB ограничения
передач. Интерактивный ring buffer — 1 MiB, ответ ≤64 KiB с has_more, transcript log
≤32 MiB с log_truncated/dropped_bytes. Непрерывный вывод не блокирует interrupt.
Эти пределы не предназначены для переноса больших файлов; прежние отчёты/readbacks не становятся новыми
сетевыми свидетельствами.

## Проверки и пределы

[SQLite/MCP/run_role/очередь/аренда/повторы/диагностика](../tests/test_task_sessions.py)
проверяют настоящий код PM/broker с заменой привилегированного process boundary
и ответа модели. SSH-forward, SSH health и VPN здесь имитируются; это не live SSH.
[Настоящие локальные workers](../tests/test_session_runtime.py) используют PTY,
Unix control sockets, двусторонний loopback TCP, EOF/обрыв, зарегистрированный
MCP transfer и файл >4 MiB. Заменена только namespace/root setup; не запускались
sudo, сканирование, внешняя цель или платный API. Полный runner отдельно сохраняет
настоящие SDK/MCP fake-API регрессии.

Воспроизведение: `.venv/bin/python tests/run_offline.py --runtime`.
Итог после исправления close от `f079c50`: 644 unittest, шесть legacy-скриптов,
ноль сбоев/пропусков; отдельные наборы содержат 24 session-manager и девять
локальных worker/file-проверок. Дополнительные [13 MCP close-регрессий](../tests/test_pivot_close.py)
не требуют sockets/netlink: заменяется только broker subprocess. Отдельные
session-наборы действительно выполнены в Kali 2026.3 с настоящими локальными
сокетами, а не пропущены или заменены socket mock. Обе самопроверки, compileall
и `git diff --check` проходят; зависимости среды не менялись. Ручные
API/инфраструктурные эксперименты не запускались, в число пройденных не входят.

Root-owned установленная копия broker не менялась. Для использования требуется
операторское обновление до session_protocol=2, pivot_protocol=1,
transfer_protocol=1. Нужен установленный OpenSSH client; новых зависимостей нет.
Параллельный workflow/нативные subagents этапа 15, универсальные туннели и
прозрачное восстановление потерянного SSH-сеанса не объявляются реализованными.
