# Специалисты coordinated: этап 15

Реализовано на базе `1de9fd03e93c99093be7f316b46029f599fb6fcf`, 17.11.2026.
PM сохраняет цели, scope, память, решения и вопросы оператора. Единственное
долговременное состояние — существующие таблицы задачи SQLite и оригиналы
материалов. Второго workflow-хранилища и фонового демона нет.

## Harness и граница исполнения

Проверка этапа 2 остаётся действительной: `deepseek-harness-sdk==0.2.1rc2`
и `runtime-bin==0.2.1rc2`, профиль sdk-minimal, не предоставляют сервисы
subagents/workflow и публичный session/cancel. Наличие плагина в runtime не
является доступностью в профиле. SDK не обновлялся.

[OwnedWorkflow в общем адаптере](../orchestrator/model_adapter.py) восполняет
недостающее: один принадлежащий ветке настоящий Harness runtime, start_session,
session.run, SDK notifications и close. ThreadPoolExecutor ограничивает число
одновременных специалистов; не исполняет команды модели. Каждый специалист
запускает существующий run_role и настоящий PM MCP через stdio. Координатор
по-прежнему использует analysis без инструментов. Native workflow/subagents,
Orca и прямой Cordis API не используются и не объявляются внедрёнными.

Модель, конфигурация адаптера и диагностический run_id наследуются через
ContextVar; ограничения инструментов пересекаются с профилем, а не расширяются.
У generic-профиля разрешены только зарегистрированные PM-инструменты: builtin
host-shell не возвращается. У каждого runtime отдельный context-файл корреляции,
поэтому параллельные MCP не присваивают друг другу request/action IDs. Один relay
на диагностический запуск живёт до завершения всех подписчиков.

## Запуск, профили и ветви

```bash
.venv/bin/python pm.py new --help
.venv/bin/python pm.py resume 1 --max-specialists 2
.venv/bin/python pm.py attack 1 --coordinated --max-specialists 2
.venv/bin/python pm.py specialists 1 --json
.venv/bin/python pm.py questions 1 --json
```

Команды с task 1 — примеры интерфейса, не выполненная разработчиком работа на
рабочей задаче. `new --coordinated`, сохранённый coordinated `resume` и
`attack --coordinated` включают этот маршрут. Начальный предел — **2**, параметр
`--max-specialists 1..10` сохраняется в pm_task_runtime; чтение паузы не мигрирует
БД. При 1 используется тот же owned lifecycle без параллельности. Старый режим
атаки сохранён. Низкоуровневый Python run() без max_specialists сохраняет прежнее
последовательное поведение для совместимости; настоящая CLI передаёт предел.

Решение использует прежнюю проверяемую схему action/role/profile/question,
boundaries, inputs/references, expected_result. Ссылки повторно разрешаются
перед запуском. Профиль задаёт процедуру, инструменты и пределы, сохраняя
исходное задание. Занятые service resource_refs и task-wide ветка не запускаются
параллельно с пересекающимися ветвями. Разные профили одной роли допустимы на
непересекающихся ресурсах. `await_specialists` допустим лишь при активных
специалистах; без изменения полезных данных модель не опрашивается по таймеру.

Веб-специалист может вызвать **pm_publish_candidate** с username, secret,
service_ref, source_ref и точной quote из сохранённого оригинала. Инструмент
локально проверяет источник и принадлежность известного сервиса текущей задаче,
атомарно публикует candidate в общей памяти. Источник должен действительно
содержать оба значения; это не автоматическое извлечение всех секретов.
Кандидат ещё не означает принятие сервером или доступ. Координатор видит
публикацию во время веб-работы и может назначить ACCESS. Проверяемый результат
ACCESS обновляет прежнее состояние доступа и триаж. VERIFY назначается для
конкретной неоднозначности; согласие двух моделей не является доказательством.

## Согласованность и остановка

- SQLite BEGIN IMMEDIATE резервирует запись до чтения версии/ключа дедупликации;
  вложенные savepoints сохраняют транзакцию вызывающего. CAS и история прежние.
  Одновременные публикации не теряют обновления, stale expected_version отклоняется.
- Проверки дедуплицируются прежним журналом операций. Пока первый одинаковый
  вызов выполняется, второй получает previous_outcome_unknown, не второй dispatch.
  Старые доказательства могут читаться, но это не новое наблюдение.
- Номера отчётов резервируются атомарно в существующих шагах; отчёты одной роли
  не перезаписываются. Чужой свежий result_id остаётся доступным источником, но
  не засчитывается как собственный новый зонд/исполнение.
  После независимой проверки `5cfe6d6` исправлена потеря владельца в проекции
  capability JSONL; подробности и отрицательное воспроизведение — ниже.
- Терминальный owner изолирован ContextVar. Существующие lease и зависимости
  session manager защищают общую интерактивную сессию; конец роли не закрывает
  полезные сессии другого владельца.
- Бюджеты остаются общими task/role: 25 основных dispatch + одобренные +5,
  PoC до 15; новый профиль не создаёт новый счёт. Расход отчёта привязан к step ID,
  поэтому два одновременных специалиста одной роли не удваивают общий расход.
- Вопрос блокирует свою ресурсную ветку, а task-wide вопрос — всю задачу.
  Ответ можно сохранить из другой консоли без повторного захвата execution lock.
  Применение привилегированного tool/pivot receipt остаётся под task lock;
  если задача работает, разрешение сохраняется, а применение требует отдельного
  --apply-tool/--apply-pivot после освобождения lock. Никакого обхода разрешений.
- Повреждённый/неполный отчёт и неизвестный исход сохраняются отдельно от успеха.
  Та же ветка требует проверки; независимая работа может завершиться.
  Неизвестная внутренняя проверка другой назначенной ветки не портит её отчёт.
- `.venv/bin/python pm.py specialists 1 --cancel 42` сохраняет запрос отмены существующего шага.
  Ещё не запущенный шаг — not_started. Запущенный runtime закрывается, новые
  активные MCP-вызовы блокируются; уже отправленная операция не объявляется
  отменённой на цели. Неизвестный исход требует проверки. Другие runtimes и
  нужные им терминалы не закрываются. Это не универсальный kill произвольного PoC.
- Session IDs/mode и cancel_requested_at сохраняются в pm_coordinator_steps.
  После аварии running автоматически не воспроизводится; saved ID не доказывает
  живость процесса и не даёт автоматического SDK resume. Штатное продолжение
  не повторяет завершённую проверку. При выполнении всех сохранённых целей
  лишние специалисты отменяются, следующего решения модели нет.

## Что проверено

[14 контрактных тестов](../tests/test_specialist_workflow.py) используют поддельные
агенты/модель, но настоящие временные SQLite и публичные MCP для публикации и
дедупликации. Проверяют CAS, владельцев терминалов, лимиты, scope ветвей,
перезапуск, planned cancellation, изоляцию неизвестного исхода и наследование
ограничений. Это не проверка настоящего агентного исполнения.

[4 runtime-теста](../tests/test_specialist_workflow_runtime.py) используют
**настоящий установленный SDK, session.run, PM MCP stdio и HTTP transport worker**.
Локальные HTTP и установленный OpenSSH sshd работают на loopback с временными
ключами; настоящий ssh подтверждается Accepted publickey и выводом id. Веб
ветка остаётся активной, пока ACCESS проверяет опубликованный кандидат. Также
проверяются отмена только одной ветки, завершение по явному platform-ответу без
лишнего решения, два профиля одной роли с расходом 2+3=5, JSONRPC stdout,
корреляция START/END, отсутствие host-shell и секретов в диагностике.

Заменены API модели (локальный SSE-имитатор) и граница привилегированного broker /
namespace: логический адрес маршрутизируется к локальным HTTP/SSH, разрешены
только объявленные fixture-команды без root. Хранилища и конфигурация временные,
storage guard запрещает доступ к рабочим данным. Реальные терминалы/lease и
передача сессии между ролями отдельно проверяются существующими
[test_task_sessions](../tests/test_task_sessions.py) и
[test_session_runtime](../tests/test_session_runtime.py); SSH в новом сценарии
одноразовый, он не подменяет проверку живого интерактивного handoff.

Не проверены настоящая CTF-цель/VPN, платный API, sudo, native workflow,
production-кэш, длительная 600-секундная операция и автоматическое восстановление
потерянного SDK runtime. Потоки Python нельзя произвольно принудительно оборвать:
контролируемая отмена действует через owned Harness close и MCP guards.
Для tool/PoC без кооперативной отмены сохраняется неизвестный исход.

## Принадлежность результатов — исправление после `5cfe6d6`

Исходный HEAD исправления: `5cfe6d6aab713da9eab87bc53feb1232fa08766c`, `main`.
Ранее MCP сохранял coordinator_step_id/actor_role, но report_probe_records
отбрасывал их. Старые runtime-тесты проверяли параллельность и суммы dispatch,
но не сопоставляли **каждый** result_id с владельцем канонического отчёта.
Прежнее утверждение об изоляции execution results было недостаточно проверено.
Новые проверки до исправления воспроизвели примесь чужого результата между
VULN/ACCESS и между двумя профилями VULN.

Теперь:

- Проекция сохраняет task/result ID, coordinator_step_id, actor_role,
  memory_operation_id, session_owner и диагностические run_id/action_id.
  Последние три метки записываются MCP при их наличии; старые строки не меняются.
- Единый фильтр `report_integrity.excluded_results` различает исходный снимок
  prior_probe_ids, новые собственные действия, чужие и неатрибутированные записи.
  В coordinated нужен совпадающий step ID; имя роли само по себе недостаточно.
  Противоречащие role/session-owner метки не принимаются за собственные.
  Отсутствующий step ID не заполняется текущим. Вне coordinated legacy-запись
  может описывать свежий результат с ownership_status=unestablished, без
  присвоения ей step ID; новые standalone-вызовы имеют session_owner.
- Фильтр применяется к execution, решению о no-action recovery, пакету
  форматирования, зависимостям, findings, гипотезам, доступу и триажу.
  После tool-free форматирования журнал перечитывается и фильтруется заново:
  другой специалист мог закончить действие за это время. При прерывании
  сохраняются только собственные квитанции; неизвестность незавершённого хода
  не превращается в успех по уже имеющимся квитанциям.
- Execution rows содержат исходные owner-метки. Новые записи без установленного
  step-владельца coordinated выводятся отдельно в unattributed_results
  (ограниченная выборка с omitted_unattributed), не среди собственных действий.
  Общая память, её индекс/агрегаты и pm_capability_read сохраняют владельцев
  исходных ссылок; само чтение явно local/fresh_observation=false.
- Общие материалы не удаляются. Все роли могут локально аудитировать чужой или
  прежний HTTP/Git-capture по оригинальным байтам, хэшу и ссылкам. Такой finding
  помечается evidence_reused/local_audit: не новое сетевое наблюдение, не новое
  закрытие гипотезы, не подтверждение доступа. Произвольный старый stdout не
  получает привилегию capture. Текущий результат владельца по-прежнему может
  обновить общую память через прежние проверки.
- Общий счёт task/role и отдельный расход по step ID не изменены. В настоящем
  same-role runtime два отчёта сохраняют расходы 3 и 2, общий счёт — ровно 5.

  same-role сценарий не оставляет ненужный поток наблюдения после завершения.
