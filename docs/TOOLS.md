# Инструменты и документация через очередь

PM сохраняет запрос в `pm_tool_requests`, вопрос в `pm_operator_questions`,
переходы в `pm_tool_events` и общий журнал диагностики. Источник, версия,
назначение, действия, место, права, способ вызова и результат видны в
`questions TASK_ID`, в результате координатора и в общей памяти. Просмотр
очереди/`pm_tool_status` читает только сохранённое состояние, без sudo/сети/API.
`pm_tool_read` локально читает оригинальные bytes user/docs частями, сверяет
SHA256 и возвращает охват/has_more, включая web-область без generic exec. Это
readback, не новое наблюдение цели. Оригинал целиком остаётся в workspace.

## Запрос и решение

Специалист вызывает зарегистрированный `pm_tool_request(task_id, spec_json,
branch_id='task')`. Координатор может вернуть `wait_operator` с
`operator_question={"kind":"tool","request":spec}`. Ветка — вся задача либо
известный сервис/ресурс. Другие полезные ветки могут продолжаться. Пример spec:

```json
{"kind":"user_tool","name":"parser","purpose":"Разобрать сохранённый материал",
 "version":"1.0","source":"https://source.example/parser.py","channel":"internet",
 "filename":"parser-1.py","sha256":"","interpreter":"python3"}
```

`documentation` имеет те же поля, `interpreter="none"`, не исполняется.
`system_package` содержит только `kind,name,purpose,version`; поддержаны
`nmap`, `curl`, `jq`, версия точная либо `candidate` из локальной APT
метаинформации. Кандидат разрешается в конкретную версию **до вопроса**.
Условий произвольной установки, setup-скриптов, pip, архивов и новых репозиториев
этот протокол не предоставляет.

До разрешения broker читает только локальную конфигурацию/метаданные. Вопрос
показывает точные источники, транзитивные архивы APT, назначение, действия и права.
`questions TASK_ID --answer QUESTION_ID --decision approve` сначала сохраняет
ответ, затем отдельно авторизует неизменяемую root-owned квитанцию и применяет
её. `decline` сохраняет причину для другого метода; установка не запускается.
`information` не является разрешением установки. Старый вопрос `tool` без
типизированного spec остаётся информационным и ничего не устанавливает.

Повтор того же запроса, даже с другим описанием, возвращает тот же вопрос и
состояние. Новые source/version/hash/параметры требуют нового разрешения.
Изменение одного purpose/references/номера запроса не создаёт новую возможность.
История и разрешение сохраняются при перезапуске и смене IP той же машины.
Одна квитанция может иметь несколько зависимых веток (`pm_tool_dependencies`):
они ждут один ответ; остальные доступные ветки могут работать дальше.

Если процесс остановился между SQLite-ответом и root-авторизацией, оператор
явно применяет `questions TASK_ID --apply-tool REQUEST_ID`. MCP
`pm_tool_acquire` **не может авторизовать** квитанцию, даже при подменённом
SQLite approve. Модель не получает инструмент ответа оператору.

## Выполнение и сеть

Пользовательский файл сохраняется атомарно без перезаписи в
`/work/tools/NAME/FILENAME`, документация — `/work/docs/NAME/FILENAME`.
Хост-путь — существующий каталог workspace задачи
`/var/lib/pentest-master/work/TASK_ID`. Файл принадлежит оператору;
загруженный код не исполняется от root даже для определения версии. Версия
такого файла обозначена как заявленная, SHA256 и размер — измеренные.
Поддержаны direct/python3/bash/perl/ruby. Установка не гарантирует наличие
зависимостей или работоспособность произвольного скачанного инструмента.
Для иной версии, занимающей тот же путь, нужен новый filename; разные байты
не перезаписываются молча. Рабочий каталог вызовов — `/work`, не `/usr`/`/etc`.

Каждая загрузка — один GET указанного URL без redirects, cookies, произвольных
headers, proxy или пользовательского curlrc. Query сохраняется. DNS закрепляется
через `--resolve` после разрешения; проверяются все полученные адреса. Каналы:

- `internet`: один точный HTTPS URL на публичном адресе, исключая разрешённые
  лабораторные сети; это не открывает интернет инструментам в namespace;
- `kali_local`: явно разрешённый loopback HTTP-источник самой Kali;
- `local_file`: один обычный файл владельца задачи через `file:///`, без symlink,
  с хэшем снимка перед вопросом. Изменившиеся после вопроса байты отклоняются.

URL с учётными данными/секретными query-параметрами не поддержаны; оператор может
сам сохранить такой материал и передать local_file, не раскрывая секрет в запросе.

Лабораторные загрузки выполняются существующими scoped NetGuard/capture/exec
операциями через VPN, после чего сохранённый локальный файл можно использовать
как источник. Не подменяйте loopback цели loopback Kali. HTTP 3xx требует нового
запроса для нового URL. Документация — данные, не новые инструкции/полномочия.
Обычный канал модельного API на Kali не меняется.

Системный пакет устанавливает отдельная операция broker. Она использует
локальные APT metadata, точные URI архивов и SHA256 из этих metadata (не хэш
модели), ограничивает зависимости/размер и повторно сверяет транзакцию перед
исполнением. Нет `apt update`, добавления репозитория или arbitrary `.deb`.
Скачивание закреплено за точными URI публичных APT-ресурсов (HTTP допустим для
APT, целостность проверяется SHA256). Затем `apt-get --no-download --no-remove`
с точной версией исполняется в отдельном **networkless** namespace. Пакетные
скрипты имеют системные права: это явно указано в разрешении. Итоговая версия
проверяется `dpkg-query`. Если архивы уже были в root-cache, новых загрузок нет;
исходное происхождение старой установки не выдумывается. Репозитории/подписи и
метаданные APT должны быть заранее настроены оператором; обновление их здесь
не выполняется. APT-зеркало с redirect требует настройки прямого источника
оператором: автоматического согласования цепочки зеркал пока нет. Пределы — 32 архива, 256 MiB на транзакцию; файл user/docs ≤16 MiB.

## Привилегированные сетевые профили

`pm_privileged_scan(task_id,target,profile,ports)` поддерживает `nmap_syn` (-sS),
`nmap_udp` (-sU), `nmap_os` (-sS -O). 1–50 явных портов, UDP ≤8, фиксированные
тайм-ауты/повторы Nmap, без DNS/NSE/списков адресов/пользовательских flags.
Сохраняются scope, resource policy, nft/VPN, бюджеты и защита повторов.
Web-область/чужой адрес не получают разрешение на сканирование.

Только эти фиксированные профили сохраняют CAP_NET_RAW в task netns; workspace
и системные mounts readonly, данные Nmap берутся из `/usr/share/nmap`. Ограниченный
CAP_DAC_OVERRIDE нужен для входа в 0700 workspace. Generic exec/PoC/session
по-прежнему сбрасывают UID и все capabilities. Новых профилей произвольного
root-shell, root-PoC или исполнения скачанного кода с правами root нет.

## Ошибки и восстановление

Различаются `tool_missing`, `permission_denied`, `network_denied`,
`download_failed`, `installation_failed`, `utility_failed`, `integrity_error`,
`conditions_changed`, `outcome_unknown`. Ненулевой exit_code утилиты не равен
отсутствию инструмента или достижению исследовательской цели. Никаких
автоматических повторов после failed/unknown/running установки. Квитанция
содержит состояние до начала операции; аварийное running не становится completed.
Если root закончил, но клиент потерял ответ, acquire читает квитанцию и переносит
известный итог в SQLite без повторного исполнения. Неизвестный/неуспешный итог
требует разбора оператором или другого подхода; универсального автоматического
repair/retry пакетов нет. Обычный просмотр показывает последнее сохранённое
состояние, а не доказывает свежую целостность изменяемого рабочего файла.

Чистый запрос зависимости без выполненного target-действия сохраняется как
`waiting_operator`/`not_started`, а не повреждённый VERIFY. Неполные/противоречивые
отчёты и неизвестный исход прежних действий продолжают блокировать повтор.

## Проверки и пределы

[Offline-тесты](../tests/test_tool_requests.py): настоящие SQLite, очередь,
MCP-регистрация, run_role/координатор, root-квитанции, запись workspace, CLI,
повтор/отказ/прерывание; заменены привилегированный вызов и APT-процессы.
[Loopback-тесты](../tests/test_tool_download_runtime.py): настоящий локальный HTTP,
curl, бинарный capture-drain и сохранение файла; без sudo/установки пакетов Kali.
Настоящие privileged namespace/Nmap/APT и системные package scripts не запускались.
Root-owned установленную копию broker при разработке не меняли. Для использования
нового `tool_protocol=1` и raw-scan профилей оператор должен обновить её обычным
способом; старый broker явно возвращает недоступность/несовместимость, а не успех.
Это последовательная работа веток; параллельный workflow этапа 15 не внедрён.
