# Единая система инструкций PM

Это используемые кодом исходники инструкций, а не отдельный набор рекомендаций.
Сборщик — [orchestrator/instructions.py](../orchestrator/instructions.py).

## Четыре слоя

1. [PM.md](PM.md) — общие правила автономности, использования находок,
   памяти, обращения к оператору, границ задания и завершения. Один и тот же
   блок включается в полный/сжатый контекст, координатор, первоначальное
   планирование, анализ Evidence Hub, вспомогательные/legacy-пути и форматирование.
   Режим analysis/format добавляет запрет действий; Harness технически отключает
   инструменты. Текст роли не отменяет этот режим.
2. [RECON](roles/recon.md), [VULN](roles/vuln.md), [ACCESS](roles/access.md),
   [VERIFY](roles/verify.md) — назначение роли. RECON обнаруживает и поверхностно
   проверяет; VULN исследует гипотезу; ACCESS решает конкретный вопрос доступа;
   VERIFY разрешает заданное противоречие/неоднозначность. Роль не является
   дополнительным разрешением или обязательной стадией каждой находки.
3. [profiles.json](profiles.json) — зарегистрированные специализации.
   У каждой есть назначение, допустимые роли, необходимые входные сведения,
   применимые процедуры, инструменты, бюджет и ожидаемый результат.
4. [procedures/](procedures/) — отдельные процедуры с границами применимости,
   происхождением доказательств и ссылками на реальные offline-проверки.
   Тело процедуры включается только при явном выборе соответствующего профиля.
   Выбор по ключевому слову URL/баннера или имени CTF не выполняется.

[tools.json](tools.json) содержит описание фактически зарегистрированных PM
инструментов. Сборщик показывает только интерфейсы выбранного профиля.
Схема JSON-отчёта и технические ограничения остаются в Python/MJS/исполнителе;
их независимых копий в Markdown нет. Дублирующиеся Python ROLES/CHARTERS теперь
лишь совместимые представления содержимого этого каталога.

## Подключение профиля

Координатор получает `specialist_profiles` и выбирает зарегистрированный
`profile` в существующем JSON-решении. Задание по-прежнему содержит `question`,
`references`, `inputs`, `boundaries`, `expected_result`; ссылки разрешаются PM
перед исполнением. Например, для VULN можно выбрать `http-surface` вместо `vuln`,
для VERIFY — `capture-audit`. Неизвестный или несовместимый с ролью профиль
отклоняется до запуска специалиста. Новые поля решения не добавлялись.

Прежний `run_role(..., assignment=None)` сохраняет профиль по имени роли.
При программном вызове тематический профиль передаётся в
`assignment['profile']` вместе с конкретными question/expected_result и
разрешёнными ссылками/данными. Произвольный путь к документу не принимается.
`inputs` профиля описывает необходимые сведения, а не доказательство их наличия:
пропуски должны быть отражены в неопределённостях. Конкретные ссылки задания
валидируются кодом; сведения из них не повышаются до фактов по названию профиля.

| Профиль | Процедура | Инструментальная граница | Потолок шага/PoC/выходных токенов |
|---|---|---|---|
| recon/vuln/access/verify | нет автоматически | наследует существующую доступность | наследует бюджет вызова |
| http-surface | http-capture | свежий HTTP с method/body/web-session, capture и чтение/память, без net_exec/PoC/PTY | 6 / 1 / 8192 |
| browser-web | browser-web | JS open/fill/click/wait/read, отдельный пользователь/владелец, HTTP и пассивный Burp; без net_exec/PoC/PTY | 12 / 1 / 8192 |
| capture-audit | capture-audit | только чтение сохранённых данных и заметки, без GET | 4 / 1 / 8192 |
| access-triage | access-triage | net_exec/session и чтение/память, без PoC/research/callback | 8 / 1 / 8192 |

Числа — потолки одного специалиста, не новый бюджет задачи. Эффективный бюджет
вычисляется как минимум сохранённого/переданного бюджета и потолка профиля;
форматирование — прежняя отдельная ограниченная analysis-попытка. Поле PoC=1
не разрешает запуск, если pm_poc_run отсутствует в tools.

Python передаёт список инструментов в `agent_actions.mjs`; Harness скрывает
неразрешённые схемы и проверяет вызов до dispatch. Предыдущее ограничение
инструментов пересекается с новым, а не заменяется более широким.
Это ограничение MCP-интерфейсов, не новый парсер всех аргументов shell/SSH.
`pm_task_memory` и `pm_material_read` входят в разрешённое локальное чтение всех
активных профилей и делят существующий read budget. Они не запускают сеть;
анализ выданного диапазона указывается отдельно в material_analysis. Детали —
[память задачи](../docs/TASK_MEMORY.md).
Task scope, NetGuard, проверки конкретной операции, триаж доступа, разрешения
и счётчики по-прежнему проверяются кодом. Профиль не устанавливает пакеты,
не получает системных/сетевых прав и не создаёт дополнительных направлений.
Параллельное исполнение остаётся этапом 15.

## Что проверено и что остаётся ограниченным

[test_instruction_system.py](../tests/test_instruction_system.py) проверяет
собираемые промпты, общий блок для всех ролей и форм контекста, исходное задание,
конкретное поручение, выбор только нужной процедуры, настоящий run_role с
подменённой границей модели, уменьшение бюджетов, автоматический ACCESS
и сохранение triage gate. Сверяет описанные инструменты с зарегистрированными в MCP.

[test_model_adapter_runtime.py](../tests/test_model_adapter_runtime.py) использует
настоящий SDK/MCP с loopback fake API: при `http-surface` схемы pm_session и
pm_net_exec отсутствуют; навязанный вызов pm_session отклоняется до MCP.
Процедуры capture/audit/triage опираются на проверки, указанные в их файлах;
это не сертификация любой команды, эксплойта или внешнего сервера.

[reference/binary-analysis.md](reference/binary-analysis.md) — тематическая
справка вместо прежних общих CTF-эвристик. Она не подключается к активному
профилю и не называется проверенной эксплуатационной процедурой.

ACCESS и использование материалов внутри задания не требуют отдельного
одобрения; специальный классификатор находок отключён как gate. Новые кандидаты
флагов автоматически направляются в очередь для ответа оператора после проверки
на платформе. Capture/VERIFY и живость цели не являются условиями ответа;
сохранённые цели и expected_flags остаются обязательными. См.
[очередь](../docs/OPERATOR_QUESTIONS.md) и
[подтверждение флагов](../docs/FLAG_CONFIRMATION.md).
Полезные сессии сохраняются общим [менеджером](../docs/SESSIONS.md), включая
[браузерные](../docs/BROWSER_BURP.md); параллельный координатор не реализован. Запрет смены
паролей действует в инструкциях и поддержанных технических проверках;
универсальный анализ произвольного SSH/PoC не доказан.
